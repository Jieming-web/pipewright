# 设计说明（design）

> 职责：如何组织系统来满足 `proposal.md` 中的需求。工作项与进度见 `tasks.md`；字段级接口定义放在 `contracts/`。

## 1. 架构总览

```
工作台（React + TS）     对话模式 ｜ 任务模式 ｜ 评审模式
      ↕  会话 API + SSE（contracts/session-api.md）
服务层（Python）         鉴权、会话管理、任务调度、事件存储、流式推送、限流与配额、
                        策略服务、子 agent 服务、skill 管理、沙箱管理、可观测
      ↕  RPC 事件（contracts/agent-events.md） ＋ 桥接口（contracts/bridge.md）
每会话沙箱容器           pi 进程（RPC 模式）＋ TS 薄桥扩展
      ↕
模型                    本地推理服务（开源权重） ／ 外部模型 API（可选）
```

核心原则：

1. **pi 当作未修改的依赖使用。** 服务层只通过 pi 的 RPC 模式（标准输入输出上逐行传 JSON）和扩展机制与它交互，不修改 pi 源码（S3）。pi 自带的能力不重做。
2. **策略判断放在 pi 进程之外。** pi 没有权限系统。TS 薄桥只负责转发：工具执行前询问 Python 策略服务，按回答放行、拦截或改写。agent 即使被 prompt injection 诱导，也改不了进程外的策略。
3. **服务层不依赖 pi 的内部细节。** 服务层把 pi 的 RPC 事件转换成本项目自己的事件协议（`contracts/agent-events.md`），存储、推送、评测、可观测都基于这套协议。以后升级 pi 或替换运行时，只需改转换这一层。
4. **代码和数据不出部署方。** 模型可以指向本地推理服务；外部 API 只是可选项。

## 3. 关键流程

### 3.1 一次任务循环

用户在工作台提交消息 → 会话 API 写入事件、交给 worker → worker 在会话的沙箱里通过 RPC 把消息发给 pi → pi 调用模型、执行工具，循环直到结束 → RPC 宿主适配把 pi 的事件转换成本项目的事件，写入存储并通过 SSE 推给工作台。

### 3.2 工具调用的权限判断

pi 准备执行工具 → TS 薄桥的 `tool_call` 钩子把调用信息发给策略服务 → 策略服务返回放行、拦截或需要确认 → 薄桥执行决定（拦截时返回原因给模型）。

- **不可用即拒绝**：策略服务连不上或超时，一律按拒绝处理，不默认放行。
- **记录耗时**：转发这一跳的耗时单独记录（R7），用评测的真实数据判断它是否影响整体延迟。
- **快速通道（后手）**：如果数据表明这一跳显著拖慢任务，把最简单、最常见的判断（如只读工具直接放行）下沉到薄桥本地完成，其余照旧转发。

### 3.3 危险操作确认

策略服务判定需要确认 → 薄桥通过 pi 的扩展弹窗发出确认请求 → 经 RPC 转给服务层 → 推到工作台，用户点"同意 / 拒绝"（可能间隔很久）→ 结果原路返回 → pi 继续执行或收到拒绝原因。确认请求设有超时，超时按拒绝处理。审计日志记录每次确认由谁做出。

**评测中的确认策略**：危险命令一律自动拒绝，在沙箱内执行的普通命令自动放行。策略写进评测配置，保证不同轮次的结果可以比较。

### 3.4 子 agent

主 agent 调用薄桥注册的子 agent 工具 → 薄桥转给子 agent 服务 → 子 agent 服务在同一个沙箱里另起一个 pi 进程，只给只读工具、全新的上下文 → 运行结束后只把摘要返回给主 agent。约束：

- **只读**：子 agent 不能修改文件，只有主 agent 能改代码。
- **深度为 1**：子 agent 的工具集里没有子 agent 工具。
- **权限只能是主 agent 的子集**，只能缩小、不能放大。
- 用评测对比"使用子 agent"与"只靠 pi 自带的上下文压缩"。

### 3.5 skill 分发

会话创建时，skill 管理按用户和团队的权限挑出可用的 skill 及其版本，放到该会话的 pi 能发现的位置，由 pi 自带机制按需加载。不另写加载机制，避免同一份 skill 被加载两次、触发来源说不清。用评测对比"挂与不挂某个 skill"的效果。

### 3.6 服务中的会话

1. 用户通过 API key 鉴权，创建会话。会话绑定用户和仓库。
2. 会话任务进入队列，由 worker 领取，并持有任务租约。
3. worker 为会话创建沙箱容器，拉取仓库，在容器里启动 pi（整个 pi 进程都在容器内，扩展也在容器内）。
4. 每一个事件和状态检查点写入 PostgreSQL。会话 API 通过 SSE 推送；客户端断线重连时携带最后收到的事件编号，服务端补发缺失的事件。
5. worker 崩溃时租约过期，其他 worker 从最近的检查点恢复任务。崩溃时正在执行的工具调用**不自动重跑**：标记为失败，并以工具结果的形式告诉模型"这次调用中断了"，由模型决定是否重试。原因是 bash 命令不一定能安全地重复执行。如何利用 pi 的会话文件做检查点，开工时确定；是否使用 pi-durable 见 proposal 第 6 节。
6. 任务结束后：任务模式提交为 PR，评审模式生成变更说明，随后销毁沙箱。

### 3.7 三种模式

| 模式 | 输入 | 后端做什么 | 输出 |
|---|---|---|---|
| 对话 | 用户的问题 | 只读会话：pi 在仓库里检索、阅读代码后回答 | 回答，附代码位置 |
| 任务 | Bug 单（描述、评论、附件、关联单） | 整理成结构化任务 → 在沙箱里定位、修改、跑测试 → 提交 PR | 可审核的 PR 和执行记录 |
| 评审 | 一个 PR | 读 diff 和相关代码，按逻辑整理 | 变更说明：修改目标、实现思路、关键 diff、影响范围、验证证据 |

三种模式共用同一套会话、沙箱、权限和事件机制，区别只在会话的初始配置（工具集、权限、提示词）和交付方式。

### 3.8 评测

- 评测在 Docker 容器中运行，每个任务使用一份独立的仓库副本，不在宿主机上直接执行 agent 的命令。
- 任务集分为开发集和留出集。开发集用于日常迭代；留出集只在每个阶段结束时运行。简历上的数字只使用留出集的结果。
- 同一任务重复运行多次，报告均值与波动。任务集本身标版本；版本变化后必须重跑基线。
- 任务来源与污染检查待定（proposal 第 6 节）。

### 3.9 本地部署与微调

- 本地推理服务提供 OpenAI 兼容接口，pi 通过 `models.json` 指向它。
- 微调用公开数据，具体数据来源待定（proposal 第 6 节）。训练数据必须与留出集隔离。
- 用同一套评测对比：外部强模型、本地模型微调前、微调后（S8）。

## 4. 数据模型

| 实体 | 说明 |
|---|---|
| 用户、团队 | 鉴权与权限归属 |
| 会话 | 绑定用户、仓库、模式；状态 |
| 事件 | 本项目事件协议中的一条输入或输出事件，带有序编号 |
| 检查点 | 用于崩溃恢复的会话状态 |
| 审计记录 | 每次策略决定、每次确认由谁做出 |
| skill 版本 | skill 内容、版本、可用范围 |
| 执行轨迹 | 一个任务从开始到结束的全部事件与指标，用于评测与可观测 |
| 评测任务 | 仓库、任务描述、判定测试、所属集合（开发集或留出集）与版本 |

字段级定义随任务推进写入 `contracts/`。

## 5. 非功能设计

### 5.1 安全与权限（R4、R6）

- **工具级**：每个工具（pi 内置工具、MCP 工具、本项目注册的工具）都有风险等级（只读、写文件、执行命令、联网），由策略服务决定放行、确认或禁止。
- **agent 级**：子 agent 只读、深度为 1，权限是主 agent 的子集。
- **会话级**：会话绑定用户和仓库；可用的 skill 按用户和团队限定；审计日志记录每次确认由谁做出。
- **沙箱级**：每个会话一个隔离容器，整个 pi 进程在容器内运行；限制资源；网络默认只允许访问模型服务和代码托管平台；只注入当前会话专用、短期有效、限定范围的凭证（例如只能向该仓库推送分支的令牌），不注入用户的长期密钥。
- **信任边界**：仓库文件、Bug 单内容和工具输出一律视为数据，不视为指令，防范 prompt injection；默认禁止访问敏感路径。

### 5.2 成本

每次运行评测或租用 GPU 前报告预计花费，运行后记录实际花费。压测使用假模型，不调用真实 API。

### 5.3 可观测（R7）

每一步记录耗时、token 和错误，包括桥接转发这一跳；能按任务回放完整轨迹。

## 7. 留给实现者决定的部分

- 薄桥与 Python 服务之间的通信方式（本地 socket、HTTP 等），只要满足 `contracts/bridge.md` 的超时与失败语义
- pi 事件到本项目事件的具体映射方式
- 本地推理服务选型（vLLM、Ollama、llama.cpp 等）
- 前端的具体库与组件（在 React + TypeScript 范围内，保持简单）
- 可观测的实现方式（OpenTelemetry 或自建 trace），只要满足 S6
- 包结构、测试框架、日志格式

## 8. 待作者复核的决定

以下是在讨论过程中由 AI 作出、作者尚未逐条确认的决定，作者可以推翻：

- 整个 pi 进程（包括扩展）运行在每会话的沙箱容器内，而不是只把工具执行转发进容器。
- 服务层把 pi 的 RPC 事件转换成本项目自己的事件协议，不直接存储和推送 pi 的原始事件。
- 沙箱网络从"拉完代码后断网"改为"只允许访问模型服务和代码托管平台"，以支持任务模式提交 PR。
- 子 agent 在同一个沙箱容器内另起 pi 进程。
- skill 分发通过把文件放到 pi 能发现的位置实现，不另写加载机制。
- 工作台排在会话 API 和沙箱完成之后再做（T6 起），先做任务模式；11 月底前不做网页，确认通过 API 完成。
