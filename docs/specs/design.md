# 设计说明（design）

> 职责：如何组织系统来满足 `proposal.md` 中的需求。工作项与进度见 `tasks.md`；字段级接口定义放在 `contracts/`。

## 1. 架构总览

可视版本：`docs/architecture/forgepilot-architecture.html`（用浏览器打开）。架构变化时，以本节文字为准，并同步更新该图。

```
① 工作台（React + TS）        对话模式 ｜ 任务模式 ｜ 评审模式
        ↕  会话 API + SSE（contracts/session-api.md）
② 统一接入 · 身份认证          SSO（OIDC，身份中心用 Keycloak 模拟）／ API key（程序用）
        ↕
③ 编排层（TS）                 理解（本地小模型）→ 校验与上下文组装 → 规则路由与装配 → 运行串联
        ↕  调用                ↕ 调用
   会话服务 ｜ 策略服务 ｜ 审批流程 ｜ 配额 ｜ skill 管理 ｜ 子 agent 服务 ｜ 事件存储 ｜ 可观测
   检索服务（MCP；内部用 Cordis 按项目装配 grep / 索引等实现）
        ↕  统一引擎接口（contracts/engine.md）
④ 执行层                      每会话沙箱容器：引擎运行器（pi SDK + 本项目扩展）
                              评测专用：Claude Code 适配器（不进产品）
        ↕
   模型                       本地推理服务（开源权重；工单理解小模型 + 主模型）／ 外部 API（可选）
```

核心原则：

1. **pi 当作未修改的依赖使用。** 通过 pi 的 SDK 和扩展机制接入，不修改、不 fork 源码（S3）。pi 自带的能力不重做；对于 `AGENTS.md` 等上下文文件，复用 pi 的加载机制，但内容来源由平台控制，并且不加载仓库内的 `.pi/` 资源（3.15.3）。
2. **编排层只发起和串联，不自己做判断。** 审批调审批流程，权限调策略服务，取消调会话服务，预算由配额模块统一扣减。每类规则只在一处定义，减少模块间依赖。
3. **模型负责理解，规则负责决定。** 本地小模型只做提取和分类建议；路由由确定性规则完成；分类结果只影响"怎么做"，不影响"能不能做"。
4. **策略判断在 Agent 引擎之外。** 引擎运行器里的扩展只负责在工具执行前询问策略服务并执行其决定，不含策略逻辑。agent 即使被 prompt injection 诱导，也改不了策略。
5. **服务层不依赖具体引擎。** 编排层、服务层和评测框架只认本项目的统一引擎接口和事件协议（`contracts/agent-events.md`），pi 和 Claude Code 各有一个适配器。引擎运行器在沙箱容器内，统一引擎接口因此是一个**跨进程协议**：后端用 TypeScript 客户端调用，评测框架用 Python 客户端调用。
6. **代码和数据不出部署方。** 产品中的模型指向本地推理服务；外部 API 只是可选项；Claude Code 只用于公开数据的评测。
7. **引擎在沙箱内运行（作者 2026-11-08 确认）。** 每个会话的沙箱容器里运行一个引擎运行器（pi SDK + 本项目扩展），后端通过网络与它通信；不采用"pi 留在后端进程、只把工具执行转发进容器"的做法，因为那样 pi 进程本身不受沙箱保护，一个会话出问题可能影响其他会话。代价是扩展询问策略服务时有一次跨容器通信，按 3.6 的要求处理。

## 3. 关键流程

### 3.1 一个工单从进入到交付

1. 员工在工作台登录（SSO）后提交工单，或开始一段对话。
2. **理解**：新工单交给本地小模型，提取结构化信息并给出分类建议（3.3）。对审批单的同意或拒绝、查询任务状态等操作类请求不经过本地模型，直接按规则处理；申请权限的工单仍需分类。
3. **校验**：编排层校验输出；关键信息缺失时，任务进入 `WAITING_FOR_INPUT`（3.5）。
4. **路由**：按分类和项目路由规则，在该员工和项目的权限范围内选择处理流程和装配（3.4）。
5. **执行**：在会话的沙箱里通过统一引擎接口运行 pi；每次工具调用前由策略服务判断（3.6）。
6. **升级**：需要从只读升级为写操作时，任务进入等待确认或审批的状态，用户确认、审批通过后才继续（3.4、3.7）。
7. **交付**：按类别交付回答、排查结论、PR、变更说明或转交记录；事件全程写入存储并推送到工作台。

### 3.2 统一接入与身份认证

- 员工通过 OIDC 登录，身份中心用 Keycloak 模拟。令牌中带有员工所属团队。
- 程序通过 API key 访问。每个 key 绑定一个员工或服务账号，权限不超过其所属主体。
- 授权链：员工 → 团队（来自身份中心）→ 项目 → 可访问的仓库与允许的操作（平台维护）。
- 在身份中心停用账号后，令牌无法续期，该员工的会话与 API key 一并失效。

### 3.3 工单理解（本地小模型）

- 输出固定字段：现象、触发条件、实际结果、预期结果、缺失信息、分类建议、把握程度；可附"疑似根因"作为线索，但不参与路由。字段定义写入 `contracts/ticket-understanding.md`。
- 每个提取字段附上它在工单原文中的出处；编排层检查出处确实存在，找不到的字段标为"未经证实"，不作为依据。
- 格式不合格时重试一次，仍不合格归为 `unknown`，交给人处理。
- 本地模型不可用或超时：跳过预处理，原始工单直接交给引擎，任务标记"未经预处理"，评测中单独统计。
- 工单内容是数据，不是指令。工单中"这是低风险任务""跳过审批"之类的文字不产生任何效果。

### 3.4 分类与路由

| 类别 | 用户想要什么 | 路由规则 | 是否改代码 |
|---|---|---|---|
| `code_qa` | 理解代码或定位某段逻辑 | 只读问答流程，检索和读取代码，输出带代码位置的解释 | 否 |
| `bug_triage` | 找出为什么出错 | 排查流程，收集代码、日志或复现证据，输出根因判断及依据；需要运行测试时按项目规则使用隔离环境 | 否 |
| `bug_fix` | 修改代码并验证修复 | 先检查写权限和审批要求，再在隔离工作区修改、测试并产出 diff；推送或创建 PR 按对应规则处理 | 是 |
| `feature_request` | 新增功能 | 整理需求和验收条件；关键需求不清先追问；引擎只读查看代码并提出实现方案；用户确认方案后检查写权限和审批要求，再启动实现 | 是 |
| `change_review` | 理解并判断已有改动 | 以指定 diff 或 PR 为输入，输出变更说明（修改目标、实现思路、关键 diff、影响范围、验证证据）以及发现的问题（位置、影响、依据） | 否 |
| `support_request` / `access_request` | 申请权限 | 收集仓库、所需权限和用途，在平台审批流程中生成审批单 | 否 |
| `support_request` / `environment_issue` | 环境故障 | 收集环境名称、报错和发生时间，生成转交记录并通知维护方；如果只发生在某个分支且能追溯到仓库配置或代码，转入 `bug_triage`；线索不足时先问"其他分支也有这个问题吗？" | 否 |
| `unknown` | 信息不足以选择流程 | 只有当不同理解会改变交付物或执行权限时，才暂停并提出一个具体问题；几种理解都只读时，选权限最小的类别直接处理 | 否 |

规则：

- **从权限最小的类别开始，升级必须确认。** 例："帮我看看这次失败，有明显问题就修一下"先路由到 `bug_triage`；得到排查结论和拟议改动后进入 `WAITING_FOR_FIX_CONFIRMATION`；用户确认后再检查写权限和审批规则，通过后才启动 `bug_fix`。
- **功能开发与 Bug 修复共用执行能力，判断标准分开。** Bug 修复要弄清"原本应该怎样，现在为什么没做到"；功能开发要定义"新增行为应该怎样，怎样才算做完"。例："加个导出按钮"要先确认导出勾选的、当前页的还是全部筛选结果。
- **"环境出问题"描述的是现象**，路由要看谁能处理、在什么范围内能处理。
- **分类可以在过程中迁移**（如 `environment_issue` → `bug_triage` → `bug_fix`），每次迁移都按当时的授权重新检查，并写入审计。
- **路由只能在权限范围内选择**，分类不能降低任何操作的风险等级。
- 路由规则写在项目配置中并标版本；每次路由记录选择结果和依据的规则版本。规则格式写入 `contracts/routing-rules.md`。

### 3.5 任务状态与等待

所有等待都使用同一套可恢复机制：

```
RECEIVED → UNDERSTANDING → ROUTED → RUNNING → DELIVERED
                ↓              ↓         ↓
          WAITING_FOR_INPUT    ↓    WAITING_FOR_FIX_CONFIRMATION
                               ↓    WAITING_FOR_PLAN_CONFIRMATION
                               ↓    WAITING_FOR_APPROVAL
任何状态 → FAILED ｜ CANCELLED ｜ EXPIRED（结束本次自动处理，工单保留，可手动重开）
```

- 进入等待状态时，记录在等什么、已经问了几轮、什么时候过期，然后**释放执行资源**（销毁沙箱、结束引擎实例）。
- 等待与过期使用**持久化的定时唤醒**：过期时间存入数据库，由调度器到点处理，不依赖进程内计时器，worker 重启不会遗漏。
- 等待用户的计时器与引擎执行命令的超时是两个独立的计时器。
- 用户回复或确认后，按任务 ID 恢复：
  - 同一类别的等待恢复时，接着原来的引擎会话，并注入"代码已更新到某提交，之前的引用可能过时"；从一个类别升级到另一个类别（如 `bug_triage` → `bug_fix`）时，开新的引擎会话，并把上一阶段的结论交给它。
  1. 合并原工单与补充内容，重新跑一遍提取；
  2. 按**恢复时**的授权重新检查权限；
  3. 重新创建沙箱、拉取最新代码；代码版本有变化时记入任务记录。
- 请求补充信息：只在缺少项目配置定义的关键信息时才问；缺的内容合并成一条消息；最多两轮。
- **超时后结束本次自动处理，保留工单，用户补充后可手动重开。用户等得久或忘了回复，都不能作为继续执行的依据。**
- **"改分类"和"授权执行"是两个操作。** 有权限的用户可以修改分类（表达意图，写入审计）；真正执行时仍按当前授权检查是否有权发起该操作、仓库是否要求审批。"确认修复"与"审批"也可能由不同的人完成。

完整状态定义写入 `contracts/task-states.md`。

### 3.6 工具调用的权限判断

引擎准备执行工具 → 扩展的工具拦截钩子把调用信息发给策略服务 → 策略服务按授权链和工具风险等级返回放行、拦截或需要确认 → 扩展执行决定（拦截时返回原因给模型）。

- **不可用即拒绝**：策略服务连不上或超时，一律按拒绝处理。
- **记录耗时**：询问策略服务这一跳单独记录（R7），用评测数据判断是否影响整体延迟。
- **快速通道（后手）**：数据表明这一跳显著拖慢任务时，把最简单、最常见的判断（如只读工具直接放行）下沉到扩展本地完成。

### 3.7 确认与审批

- **确认**：策略服务判定需要确认 → 经引擎事件推到工作台 → 用户点"同意 / 拒绝" → 原路返回。确认有超时，超时按拒绝处理。
- **长时间未答复的确认**：工具确认超过 10 分钟未答复时，任务转为 `WAITING_FOR_CONFIRMATION` 并释放资源（引擎会话文件已持续落盘）；答复后恢复，被挂起的工具调用按答复执行或拒绝。
- **审批流程**（权限申请、修复确认、方案审批、仓库要求的审批共用）：
  - 申请人不能批自己的单；
  - 审批人必须对相应仓库或项目有审批权（由项目配置定义）；
  - agent 永远不能审批或授权，最多帮忙填写审批单；
  - 授权可以设有效期，到期自动回收；
  - 申请、批准、生效、回收全程审计。
- **评测中的确认策略**：危险命令一律自动拒绝，在沙箱内执行的普通命令自动放行。T3 之前用评测配置中的临时危险命令清单判定，T3 起由策略服务替换。策略写进评测配置。

### 3.8 子 agent

主 agent 调用本项目注册的子 agent 工具 → 子 agent 服务在同一个沙箱里另起一个引擎实例，只给只读工具、全新的上下文 → 运行结束后只把摘要返回给主 agent。约束：只读；深度为 1；权限只能是主 agent 的子集。用评测对比"使用子 agent"与"只靠 pi 自带的上下文压缩"。

### 3.9 skill 分发

会话创建时，skill 管理按用户和团队的权限挑出可用的 skill 及其版本，放到该会话的 pi 能发现的位置，由 pi 自带机制按需加载。不另写加载机制。用评测对比"挂与不挂某个 skill"的效果。

### 3.10 服务中的会话

1. 员工登录后创建会话，会话绑定员工、项目、**一组仓库**和模式；创建时逐个检查该员工所在团队是否有权访问这些仓库。写操作类的任务（`bug_fix`、`feature_request`）一次只绑定一个可写仓库；其余仓库只读（3.16）。
2. 会话任务进入队列，由 worker 领取，并持有任务租约。
3. worker 为会话创建沙箱容器，拉取仓库，在容器里启动引擎运行器。
4. 每一个事件和状态检查点写入 PostgreSQL。会话 API 通过 SSE 推送；客户端断线重连时携带最后收到的事件编号，服务端补发缺失的事件。
5. worker 崩溃时租约过期，其他 worker 从最近的检查点恢复任务。崩溃时正在执行的工具调用：工具风险等级表中声明为**可安全重跑**的（只读类，如读文件、搜索）直接重跑；其余（bash、写文件等有副作用的）**不自动重跑**，标记为失败并以工具结果的形式告诉模型"这次调用中断了"，原因是这类命令不一定能安全地重复执行。**崩溃循环保护**：同一任务被崩溃打断达到上限（默认 5 次）即终止并报告，不再被领取。引擎层的检查点使用保存到沙箱外的 pi 会话文件（3.14）。设计借鉴 pi-durable，但不采用它（`decisions/012-pi-durable-not-adopted.md`）。
6. 任务结束后按类别交付，随后销毁沙箱。

### 3.11 评测

决策见 `decisions/011-evaluation-data-sources.md`。

**通用规则**

- 评测在 Docker 容器中运行，每个任务使用一份独立的仓库副本。
- 任务集分为开发集和留出集；简历上的数字只使用留出集的结果。同一任务重复运行多次，报告均值与波动。任务集标版本。
- 不引用第三方排行榜的分数。

**数据来源**

| 用途 | 来源 |
|---|---|
| 端到端开发集（`bug_fix`） | SWE-bench Verified 子集（30–50 个，覆盖多个仓库） |
| 端到端留出集 | SWE-bench-Live full 划分中，所用模型训练截止日期之后（再留几个月余量）的新任务；若 Live 停止更新，改用 SWE-rebench 的按月划分 |
| 检索评测 | 上述任务中修复 PR 改动的文件，以及合成任务中注入 Bug 的位置 |
| 工单分类、提取测试集 | 同一批仓库的原始 issue（含咨询、无效报告、功能请求），人工标注 |
| 工单理解微调训练集 | 其他仓库的 issue，由强模型标注并人工抽查，加上合成工单；与测试集仓库不重叠 |
| 合成 Bug 任务 | 借鉴 SWE-smith：在真实仓库中注入 Bug，只保留确实使原本通过的测试失败的改动，再由模型根据补丁与失败测试写症状描述 |
| 其他类别 | 合成：`code_qa`、`feature_request`、`change_review`、`support_request`、等待补充信息（删去真实 issue 的关键信息）、跨仓库小型服务组 |
| 中毒测试集 | 合成：恶意工单、恶意仓库内容、恶意粘贴、任务分支修改 `AGENTS.md`、仓库放置 `.pi/` 扩展 |

**防止"见过题目"与"提前看到答案"**

1. 留出集只用训练截止日期之后的任务；更换模型时同步更换留出集。
2. **检索的时间截断**：评测中代码索引与提交历史检索只能看到任务基准版本之前的内容。
3. PR 描述与评审意见只能看到 issue 创建时已存在的内容。
4. 开发集的绝对分数可能偏高，报告中注明，只用于相对比较。

**合成数据的规矩**

- 标准答案尽量可由代码核对："先造答案、再出题"（如注入 Bug 后由模型写症状）。
- 每个任务自动验证（注入后测试失败、恢复后通过；引用的代码位置存在），每批按比例人工抽查。
- 生成任务的模型与被评测的模型分开（不得用 Claude 生成再评 Claude Code）；报告注明生成模型。
- 报告注明哪些结果来自合成数据；测试集与留出集优先使用真实数据或"先造答案"的数据。

**运行环境**

- Mac：先试 Epoch AI 提供的 arm64 镜像（实验性质），不可用则本地构建，只跑少量冒烟测试。
- x86 云服务器（只需 CPU）：基线、2×2、留出集等正式评测。
- GPU 服务器：微调与本地推理部署期间租用，可同时承担评测。
- 沙箱管理支持在远程 Docker 主机上创建容器，评测框架不因运行位置而改变。
- 租用前报告预计花费，结束后记录实际花费。

**对比实验**

- **两种运行方式**：直接通过统一引擎接口运行（不经过编排层），以及经过编排层运行（T6 提供）；2×2 中"有编排层"一组使用后者。
- **模拟用户**：经过编排层运行时，等待状态由固定策略回答——补充信息用被删去的原文作答，确认与审批自动通过（危险命令仍拒绝）；策略写进评测配置，保证轮次之间可比。

- **2×2**：pi / Claude Code × 有无编排层。同一引擎内比较有无编排层，引擎强弱的差异互相抵消；Claude Code 单独运行代表"通用工具"基线。是否加一组"pi + Claude 模型"见 proposal 第 6 节。
- **工单理解**：分类准确率（单独统计危险方向的误分类，如把只读排查分成修复）、提取准确率与编造率（出处在原文中找不到）。
- **小模型 vs 主模型**：同一批数据上比较本地小模型（微调前后）与主模型的准确率、成本、延迟。
- **功能开发的判定**：先把验收条件写成测试，测试通过才算完成。

### 3.12 本地部署与微调

- 本地推理服务提供 OpenAI 兼容接口，pi 和编排层通过配置接入。
- 首个微调对象是工单理解小模型（LoRA）。训练数据可由强模型批量标注公开 issue 并人工抽查；测试集必须人工标注，且来自训练数据中没有出现过的仓库。
- 用执行轨迹微调整个 agent 以后再定。

### 3.13 代码检索

- **使用与管理分开**：引擎（pi、Claude Code）通过 MCP 调用检索工具；索引的构建、更新、选择由平台侧的检索服务负责，不放在 pi 扩展里（pi 扩展随会话结束，无法长期持有和共享索引）。
- **按项目选择实现**：第一版至少两种代码检索实现（如 grep 与一种索引，具体种类开工时定），由项目配置决定；配置改变时切换实现，不重启后端，不影响其他项目。
- **提交历史检索**：第一版即提供，覆盖提交信息与 diff（数据在仓库内，可离线获取），用于查找过去的修法，是长期记忆"不存修法"的前提（3.15）。PR 描述与评审意见以后再接入，它们是不可信数据，只能作为检索结果供 agent 参考，不能成为记忆的依据。
- **Cordis 只用在这里**：每种检索实现是一个插件，声明自己依赖的服务（如嵌入模型、存储、代码分析工具）；卸载时自动停止它的后台建索引任务、仓库监听和定时器。
- **权限**：检索结果按会话的仓库授权过滤，员工检索不到无权访问的仓库。
- **评测**：在不同规模的公开仓库上比较各实现找全相关文件的比例、耗时、成本（S11），报告写明仓库规模。
- **按仓库读文件**：检索服务通过 MCP 提供按（仓库、路径、版本）读取文件的工具，供 pi 读取未检出到沙箱的仓库；已检出的仓库仍用 pi 自带的 `read`。
- 接口写入 `contracts/retrieval.md`。

### 3.14 会话的两层

会话记录分两层，分界线是：**给模型用的记录归 pi，给人和平台用的记录归本项目。**

| | 引擎会话（pi） | 平台会话（本项目） |
|---|---|---|
| 记录什么 | pi 与模型之间的对话：系统提示词、每轮模型输出、工具调用与结果、压缩摘要、分支 | 员工与平台之间发生了什么：提交人、项目与仓库、工单原文、提取结果、分类及修改、任务状态迁移、确认与审批、推送事件（带序号）、审计、交付物 |
| 作用 | 让引擎知道自己做到哪里，组装下一轮请求的上下文 | 让人看得到、查得到、接得上：重新进入时加载历史、断线补发、追溯过程 |
| 存储 | pi 自己的会话文件，格式由 pi 决定 | PostgreSQL |
| 粒度 | 一次引擎执行一份 | 一个平台会话可包含多次引擎执行（如先 `bug_triage`、等待确认、再 `bug_fix`） |
| 谁实现 | pi，不修改、不重写 | 本项目 |

- pi 的事件经适配器转换后也写入平台会话，工作台的流式输出与工具时间线由此而来；平台会话不负责为模型组装上下文。
- **引擎会话文件保存在沙箱之外**：pi 会话文件写在挂载到沙箱之外的存储上，持续落盘；沙箱崩溃、销毁或任务进入等待后，重建沙箱时放回，使等待恢复与崩溃恢复能接着原来的上下文继续。
- 保存会话不等于自动恢复所有正在运行的进程；任务恢复按 3.5 与 3.10 的机制进行。

### 3.15 策略、规则与长期记忆

决策见 `decisions/008-policy-rules-memory-layers.md` 与 `decisions/009-long-term-memory.md`。

#### 3.15.1 三层划分

| | 管什么 | 例子 | 违反了算错吗 | 谁决定 | 怎么失效 | 用之前要核对吗 |
|---|---|---|---|---|---|---|
| **策略**（硬约束） | 能不能做 | "支付模块 2026-12-31 前冻结，只允许修 P0" | 做不到，代码拦截 | 项目管理员 | 管理员修改配置 | 不用，代码强制执行 |
| **规则**（软约束） | 应该怎么做 | "集成测试必须连真实数据库"、"我们用 pnpm" | 算错，要修正 | 团队，经代码评审 | 只有明确修改才变 | 不用，直接遵守 |
| **记忆**（参考） | 做的时候要知道什么 | "订单告警看板在 Grafana 的 order-prod 页" | 不算错 | 观察到、说出来的事实 | 会过时，有有效期 | 要，与现状冲突以现状为准 |

- 判断依据：这句话是在"要求"agent，还是在"告诉"agent。要求中涉及"允许改什么、能访问什么"的是策略，其余是规则；告诉 agent 的是记忆。
- 归类由模型判断，代码只打标记，拿不准的交给确认环节；不按关键词机械判断（"我们用 pnpm"是规则，"这次必须先修登录"只是一次性的任务要求）。
- **例外**：个人偏好允许是要求句式（如"以后用中文回答"），它属于个人，不进团队规则，仍放在记忆中，范围只限本人。

#### 3.15.2 策略层

- 放在平台的**项目策略配置**中，由项目管理员维护，带版本和审计；由策略服务执行（3.6）。
- 内容：冻结期及冻结期内允许修改的范围、禁止访问的目录与文件、需要审批的操作及审批人、工具风险等级、团队/项目/仓库授权。
- 工单、记忆、`AGENTS.md` 都不能覆盖策略。

#### 3.15.3 规则层

- 放在仓库的 `AGENTS.md`：跟着基准分支走、修改走代码评审、人与 agent 共用。
- **规则只认基准分支**：启动 pi 时关闭对 `AGENTS.md` 的自动发现（`--no-context-files` 或等价设置）；平台从任务分支所基于的受保护分支读出 `AGENTS.md`，通过 pi SDK 的 `resourceLoader` 提供给 pi。任务分支中对 `AGENTS.md` 的改动在合并前不算规则。这复用了 pi 的上下文文件机制，只是由平台控制内容来源。
- **禁用仓库的 `.pi/` 资源**：被处理的仓库一律视为不信任，不加载其中的项目配置、系统提示词追加、扩展、skill；本项目的扩展、skill 和提示词补充只由平台注入。具体开关在 T1 开工时核实（pi 在加载项目资源前会做项目信任判断）。
- 规则不能覆盖策略。
- **"必须"类纠正的出口**：项目或团队范围的要求不进记忆。第一版在对话中给出建议写入 `AGENTS.md` 的草稿，由用户自己提交；同时作为提出者本人"试用中"的内容生效，`AGENTS.md` 合并后自动删除。第三版由 agent 自动生成修改 `AGENTS.md` 的 PR。

#### 3.15.4 记忆的定位与类型

只存从当前代码、提交历史、`AGENTS.md`、已有文档里推不出来的东西。pi 没有长期记忆（只有静态的上下文文件），由本项目实现。

| 类型 | 存什么 | 例子 | 可见范围 |
|---|---|---|---|
| 背景 | 目标、期限、约束的来龙去脉 | "项目目标是 2027 Q1 上线海外支付，所以多币种优先" | 项目 |
| 原因 | 为什么这样决定（规则里没写到的部分） | "当初放弃 MongoDB，是因为审计要求强事务" | 项目 |
| 资料位置 | 外部资料、看板、手册在哪里 | "订单告警看板在 Grafana 的 order-prod 页" | 项目或团队 |
| 经验 | 环境、构建、测试方面的坑与验证过的做法 | "这个仓库的测试要先启动 Redis 容器，否则 30 秒后超时失败" | 项目 |
| 个人偏好 | 员工的背景、习惯与个人要求 | "以后用中文回答" | 只有本人 |

**不存**：代码结构、约定、文件路径；提交历史；代码层面的修法（交给提交历史检索，3.13）；`AGENTS.md` 与已有文档中已有的内容；任务进度与临时状态；工单、仓库文件、工具输出、粘贴内容的原文；模型的推测；项目和团队范围的要求（走规则）。用户要求记住一份 PR 列表时，只记其中意外、不明显的部分。

**一条记忆的字段**：标题；描述（一句话，写清何时该用，召回时据此判断相关性）；类型；正文（"原因""经验"写明适用条件；任何类型的正文都不放仓库内路径，只有"资料位置"允许外部 URL）；范围；依据（人的原话：消息 ID + 原话片段；或执行结果：工具调用记录 ID）；状态（候选 / 试用中 / 生效 / 待复核 / 已过期 / 已删除 / 冲突待裁决）；有效期；关联文件（元数据，只用于过期检测，不注入模型、不算正文）；绝对日期；版本历史。存放在 PostgreSQL。接口写入 `contracts/memory.md`。

#### 3.15.5 写入

```
触发 → 前置过滤 → 生成候选 → 代码检查 → 去重 / 冲突 → 确认或试用 → 批准 → 生效
```

**触发入口**

1. **主 agent 主动提议**：pi 扩展注册 `memory_propose`（提议新增、更新、删除）与 `memory_expand`（按 ID 展开全文）；记忆规则由平台注入的提示词补充告知模型，由模型判断何时调用。`memory_propose` 只产生候选，不直接写入。
2. **每轮结束后台提取**：引擎报告本轮已结束且不会继续时，经前置过滤后放入队列，由 worker 执行；本轮已有提议则跳过；游标存在 PostgreSQL，按"会话 + 事件范围"幂等；每个会话最多一个排队任务，新的覆盖旧的；后台 agent 只能读该会话的平台记录、只能调用提议接口，不能访问仓库或执行命令；有轮数与超时上限。
3. **被结果验证的经验**：依据为平台记录的执行状态（如同一命令先失败、改参数后成功），服务端核对两条记录存在且结果一败一成；核对的是执行状态而非输出文字。只收环境、构建、测试方面的坑。因先后不等于因果，首次出现只对本人试用；多个会话重复出现或经人确认后才进入项目审批。

**前置过滤**（由记忆服务负责，满足任一才入队）：用户说了足够长的话、出现"失败后成功"的工具调用、会话闲置一段时间且累计足够多用户消息——这三条由代码判断；出现纠正、否定、表态——这一条由记忆服务调用本地推理服务上的小模型判断。记忆服务使用未微调的基础版小模型（T13 微调的工单理解模型专用于提取与分类，是否可共用以评测为准）。阈值用数据确定。

**代码检查**

- 拒绝：必填字段缺失或类型不合法；依据不存在；依据为消息但不是人发送的；原话片段不是该消息原文的子串；像指令的内容（跳过审批、提高权限、忽略规则；个人偏好同样检查）；正文含仓库内路径或非"资料位置"类型含外部 URL；与受保护分支 `AGENTS.md` 或已有文档重复（经检索服务比对）；范围越权。
- 只打标记、交给确认环节：疑似粘贴内容（长文本、代码块、日志、邮件格式）；"要求"与"告诉"的归类；看起来像提交摘要或活动总结。

**去重与冲突**：与同范围已有记忆说同一件事则转为更新提议；与已有记忆矛盾则标"冲突待裁决"交人处理；与规则矛盾以规则为准。

**确认、试用与审批**

| 范围 | 生效方式 |
|---|---|
| 个人偏好 | 本人再点一次确认才生效；界面并排显示原话与提取结果 |
| 项目或团队 | 提出后立即对提出者本人生效（试用中），审批通过后扩大到整个项目 |
| "必须"类项目纠正 | 给出 `AGENTS.md` 草稿，本人试用，合并后自动删除 |
| 被结果验证的经验 | 先对本人试用；重复出现或经人确认后进入项目审批 |

- 试用中 30 天未批准自动过期，并在批量清单中提示。
- 批量审批：候选汇总成周报式清单，审批人一次处理，每条并排显示原话、提取结果与警告标记。
- 第一版最小界面：对话内确认 + 简单的待审批列表；完整记忆页面在第二版。审批复用平台审批流程（3.7），全程审计。

#### 3.15.6 召回

- 时机：任务开始或对话模式每个新问题到来时；过程中可调用 `memory_expand`。
- **第一版**：注入当前员工在当前项目可见的、状态为"生效"或"本人试用中"的全部记忆的标题与一句话描述，由模型判断是否展开（PACE 多粒度思想的最简版本）。
- **分层挑选**（第三版）：某项目超过 100 条记忆或描述总长超过阈值时启用：权限过滤 → 关键词与本地向量粗筛（查询为工单提取结果 + 当前步骤）→ 记忆服务调用本地推理服务上的小模型精选 → 按相关性决定详细程度（借鉴 PACE，Wei et al., ACL 2026）。持续记录每个项目的记忆条数。
- **注入方式**：以消息形式追加在上下文末尾，已注入的不改不删，保护提示词缓存；不放进系统提示词。附固定说明："这些是过去某个时间点的记录；涉及当前文件、配置、状态时先核对；与现状冲突以现状为准，并提交更正。"pi 扩展的上下文钩子能否只追加，在记忆第一版开工前核实。
- **按谁召回**：个人偏好只按当前发消息的人召回；多人会话不注入个人偏好；用户要求本次不用记忆时完全不注入、不引用。
- 召回按仓库与项目授权过滤。

#### 3.15.7 维护

- 有效期到期自动"已过期"；有有效期的按有效期处理。
- 无有效期的项目和团队记忆每 90 天提醒复核。
- pi 使用时发现与现状矛盾，提交更正或删除候选。
- （第三版）检索服务增量更新索引时通知关联文件已变化的记忆，标为"可能过期"。
- （第三版）定期整理：按项目，距上次至少 24 小时且至少 5 个新会话时触发，数据库锁保证互斥；只产出修改提议，汇入批量清单。
- （第三版）升级为规则：同一经验或纠正被反复确认（如来自三个不同的人）时，由 agent 生成修改 `AGENTS.md` 的 PR，合并后删除对应记忆。
- 员工离职时直接删除其个人偏好。

#### 3.15.8 与检索服务的关系

记忆服务调用检索服务，两者不合并；记忆服务只有一种实现，不使用 Cordis。

- 提交历史检索（T7）是"不存修法"的前提。
- PR 描述与评审意见以后再接入；它们是不可信数据，只能作为检索结果供参考，不能成为记忆的依据。
- 写入时经检索服务与已有文档比对。
- （第三版）索引更新提供过期信号；分层召回共用检索服务的嵌入模型与向量存储。

#### 3.15.9 可靠性

提取与整理是队列中的后台任务，worker 崩溃可重试；游标存在数据库，按"会话 + 事件范围"幂等；写入使用事务，记忆与其版本记录一起提交；保留历史版本可回滚。

#### 3.15.10 评测

| 评测 | 阶段 | 说明 |
|---|---|---|
| 同一个纠正被重复说的次数 | 记忆第一版 | 个人偏好、项目试用、`AGENTS.md` 草稿三条路径应使次数明显下降 |
| 中毒测试 | 记忆第一版 | 恶意工单、恶意仓库内容、恶意粘贴、任务分支改 `AGENTS.md`、仓库放置 `.pi/` 扩展，均不能变成生效的记忆、规则或代码执行 |
| 转述准确率 | 记忆第一版 | 提取结果与原话意思是否一致；同时用于决定提取模型 |
| 有无记忆的成功率 | 记忆第二版 | 在依赖背景信息的任务上对比 |
| 召回准确率 | 记忆第三版 | 记忆量增大后 |

#### 3.15.11 单任务内部的上下文管理

第一版用 pi 自带的压缩。若评测显示较多长任务因上下文管理失败，再用 pi 扩展实现 PACE 式选择，与 pi 自带压缩做对比实验。

### 3.16 跨仓库只读

决策见 `decisions/010-cross-repo-read-only.md`。

- **范围**：第一版支持沿调用链跨几个相关仓库的**只读**问答与排查（`code_qa`、`bug_triage`），交付一条带代码证据的调用链。全公司范围的代码搜索、跨仓库修改不在第一版。
- **选仓**：用户在本次对话中显式选择仓库；编排层逐个检查读取权限。第一版不自动发现服务依赖。"跨仓库"指跨本次对话选中的仓库。
- **对话模式的分类**：对话模式只在只读类别（`code_qa`、`bug_triage`）之间分类；需要修改代码的请求提示用户切换到任务模式。
- **扩大范围**：pi 发现需要查看未选中的仓库时，只能说明理由并提出建议；由用户把仓库加入本次对话，编排层核对权限并写入审计（谁加入、为什么）。agent 不能自行扩大可见范围；仓库内容诱导 agent 读取其他仓库，也只能形成建议。
- **不全部检出**：只读问答依靠代码索引与检索服务的按仓库读文件工具；需要运行测试或复现时，再把对应仓库检出到沙箱。
- **固定版本**：会话开始（或仓库加入）时记录每个仓库的分支与提交；证据写成"仓库@提交:文件:行号"，对话期间仓库有新提交也不影响已引用的证据。
- **如实标注**：调用链的每一跳都要对应到具体仓库与代码位置；找不到下一跳的实现时，把链路标为"只验证到这里"。
- **规则**：按仓库分别注入各自基准分支上的 `AGENTS.md`，注明来源仓库。
- **修改仍是单仓库**：排查发现需要改多个仓库时，拆成多个单仓库任务分别交付。
- **评测**：调用链完整度（标为已验证的每一跳是否正确）；显式选仓打断排查的频率（agent 请求加仓库的次数）。

### 3.17 自我改进循环（RSI）

决策见 `decisions/013-self-improvement-loop.md`。属于 L2 策略自主：人设定目标、评估标准与边界，系统自己归因、提出改进并验证，人审批后生效。

```
跑评测 → 汇总失败与轨迹 → 按根因分类，挑影响最大的一类 → 提出一处改动（PR）
      → 开发集前后对比（重复多次）→ 人审批合并 → 留出集定期复核
```

- **根因与改进方式**：知识缺失 → 记忆或检索配置；策略错误 → 提示词补充或路由规则；工具问题 → 记录（第二档才改工具代码）；模型能力不足 → 记录，由作者决定是否微调。
- **可修改范围分档**：第一档为 skill 文本、提示词补充、路由规则、检索实现选择与参数、经验记忆；第二档（以后）为工具与扩展代码，必须在沙箱验证并人审；**永远不可修改**：评测集、判分逻辑、策略服务、权限、审批、工具拦截扩展。
- **采纳标准**：改善超过波动范围；转人工比例、追问次数、成本等指标没有明显变差（防止"刷分"，如把难题都分到无法判断）；其他任务没有退步。
- **控制**：作者手动触发；每轮预算上限并先报预计花费；轮数上限与"连续若干轮提升低于阈值"自动停止；每次只改一处；被采纳的改动可按版本回滚。
- **不照搬**：无真实业务流量，不做线上灰度，以开发集验证加留出集复核代替；模型层的自动微调不在循环内。
- **记录**：每一轮的归因、提议、对比数据、是否采纳写进评测报告，包括未被采纳的结果。

## 5. 非功能设计

### 5.1 安全与权限（R4、R6）

- **身份级**：员工通过 SSO 登录；程序用绑定到主体的 API key；停用账号即失效。
- **工具级**：每个工具（pi 内置工具、MCP 工具、本项目注册的工具）都有风险等级（只读、写文件、执行命令、联网），由策略服务结合授权链决定放行、确认或禁止。
- **agent 级**：子 agent 只读、深度为 1，权限是主 agent 的子集；agent 不能审批或授权。
- **会话级**：会话绑定员工、项目和仓库；可用的 skill 按员工和团队限定。
- **沙箱级**：每个会话一个隔离容器，引擎运行器在容器内运行；限制资源；网络默认只允许访问模型服务、策略服务和代码托管平台（自建 Gitea）；只注入当前会话专用、短期有效、限定范围的凭证，不注入长期密钥。
- **信任边界**：仓库文件、工单内容、工具输出、粘贴内容、PR 评审意见一律视为数据，不视为指令；模型分类与记忆都不能代替或影响权限判断；默认禁止访问敏感路径。
- **规则与仓库资源**：`AGENTS.md` 只取自任务分支所基于的受保护分支，由平台注入；不加载仓库内的 `.pi/` 资源（配置、提示词追加、扩展、skill），防止仓库内容在引擎进程中执行代码（3.15.3）。
- **项目策略**：冻结期等硬约束放在项目策略配置中，由策略服务执行，规则与记忆都不能覆盖。

### 5.2 成本

每次运行评测或租用 GPU 前报告预计花费，运行后记录实际花费。压测使用假模型，不调用真实 API。

### 5.3 可观测（R7）

每一步记录耗时、token 和错误，包括理解、路由、每次工具调用与策略询问；能按任务回放完整轨迹。
