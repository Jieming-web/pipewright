# 008：策略、规则、记忆三层

- **状态**：已确认
- **日期**：2026-11-08
- **相关**：proposal.md R6、R13 ／ design.md 3.6、3.15、5.1

> 本记录确认后不再修改正文。改变决定时，新写一份记录，并把本记录的状态改为"已被 NNN 取代"。

## 背景

设计长期记忆时发现，"项目记忆"里混着三种性质不同的东西：必须由代码强制的约束（如冻结期）、团队要求的做法（如"集成测试必须连真实数据库"）、帮助判断的背景事实（如看板在哪里）。设计中已有一条底线"记忆永远不能影响权限判断"，如果冻结期放在记忆里，策略服务不会理会它，agent 照样能修改冻结模块。

同时发现两个安全问题：pi 默认从工作目录加载 `AGENTS.md`，即任务分支检出的版本，agent 或工单可以借此改写规则；pi 还会加载仓库中 `.pi/` 下的项目资源，其中扩展会在 pi 进程内执行代码。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 全部放进记忆 | 一套机制 | 冻结期等约束无法强制执行；要求和事实混在一起，审批标准不统一 |
| B. 记忆 + 策略两层 | 硬约束可强制 | 团队规范没有合适的位置，要么当记忆（会过时、要核对），要么当策略（太重） |
| C. 策略 + 规则 + 记忆三层 | 每层的决定者、失效方式、是否核对都不同，各得其所；规则可复用代码评审 | 需要处理规则来源的信任问题 |

## pi 的做法

pi 会从代理目录、工作目录及其上级目录加载 `AGENTS.md` / `CLAUDE.md` 等上下文文件，可用 `--no-context-files` 关闭自动发现，SDK 的 `resourceLoader` 允许宿主提供或替换上下文文件。pi 会在加载项目资源（配置、扩展、skill 等）前做项目信任判断。pi 没有权限系统和长期记忆。

## 决定

采用方案 C：

- **策略**（能不能做）：项目策略配置，项目管理员维护，策略服务执行；工单、记忆、规则都不能覆盖。
- **规则**（应该怎么做）：仓库中的 `AGENTS.md`。只取任务分支所基于的受保护分支上的版本，由平台通过 `resourceLoader` 注入，关闭 pi 的自动发现；任务分支中的改动在合并前不算规则。
- **记忆**（做的时候要知道什么）：记忆服务（见 009）。
- 不加载仓库内的 `.pi/` 资源；本项目的扩展、skill、提示词补充只由平台注入。
- 归类由模型判断、代码打标记、拿不准交给确认环节；个人偏好允许是要求句式，仍属于记忆。
- 第一版为项目范围的"必须"类纠正提供出口：给出 `AGENTS.md` 草稿由用户提交，同时对提出者本人试用。

## 理由

- 三层在"谁决定、怎么失效、用前是否核对"上完全不同，分开后每层的审批与执行方式都清楚。
- 规则放在仓库里可以跟着基准分支走、复用代码评审，人和 agent 共用；只认受保护分支解决了任务分支被篡改的问题。
- 复用 pi 的上下文文件机制，只控制内容来源，不违背"pi 自带的不重做"。
- 禁用仓库 `.pi/` 资源堵住了仓库内容在引擎进程中执行代码的路径。

## 后果

- T1 需要关闭 `AGENTS.md` 自动发现、改由平台提供，并禁用仓库 `.pi/` 资源；具体开关开工时核实。
- T3 需要增加项目策略配置（冻结期等）。
- 记忆写入时需与受保护分支的 `AGENTS.md` 比对去重；与规则矛盾时以规则为准。
- 中毒测试需覆盖"任务分支修改 `AGENTS.md`"与"仓库放置 `.pi/` 扩展"。
