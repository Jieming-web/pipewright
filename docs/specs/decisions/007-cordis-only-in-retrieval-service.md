# 007：Cordis 只用在检索服务内部

- **状态**：已确认
- **日期**：2026-11-08
- **相关**：proposal.md R12 ／ design.md 第 1 节、3.13 ／ 003（其中"编排层使用 Cordis"的理由由本记录修正）

> 本记录确认后不再修改正文。改变决定时，新写一份记录，并把本记录的状态改为"已被 NNN 取代"。

## 背景

作者的架构图中有"Cordis 插件化执行层"，并希望引入 DeepSeek Harness（dsh）的插件化思想。dsh 是 DeepSeek 开源的 agent harness（TypeScript，MIT，开发者预览版），建在 Cordis 之上，"一切皆插件"，连 agent loop 都是插件。

但本项目已经复用 pi 作为引擎，pi 本身也有扩展机制。作者提出的判断标准是：**只有存在平台级的复用需求，才值得引入 Cordis；如果某项能力只有 pi 在用，就用 pi 扩展。**

## 备选方案

逐个检查 pi 之外可能需要插件化的位置：

| 位置 | pi 扩展能否覆盖 | 第一版是否有多个实现 | 结论 |
|---|---|---|---|
| 检索服务内部：按项目选索引 | 不能（索引的构建、维护、选择在 pi 之外，长期运行，跨会话、跨引擎共享） | 有，至少两种 | 用 Cordis |
| 按项目装配平台能力（模型、引擎、交付目标、审批规则） | 不能 | 部分有 | 第一版用接口 + 项目配置 |
| 企业外部系统接入（工单来源、代码托管、身份中心、通知） | 不能 | 没有 | 以后再说 |
| 平台事件订阅者（审计、可观测、评测轨迹、记忆写入） | 只能覆盖 pi 内部事件 | 有 | 普通事件总线即可 |
| 引擎适配器（pi / Claude Code） | 不能 | 有两种 | 简单工厂即可 |
| 编排层流水线阶段、工作台前端 | — | 没有 | 过度设计 |

另外考虑过"以 dsh 为底座"和"引擎换成 dsh"：dsh 已自带沙箱、审批、子 agent、skill 等，与 pi 定位重叠，且处于预览期、接口不稳定，均不采用。

## pi 的做法

pi 有自己的扩展机制（注册工具、拦截工具调用、事件钩子），作用范围是单个 pi 会话进程，生命周期随会话结束。pi 没有长期运行、跨会话共享的服务层。

## 决定

- agent 循环内的扩展（工具拦截、注册本项目工具）用 **pi 扩展**。
- 需要跨引擎、跨层复用的检索能力，以 **MCP 服务**的形式提供给 pi 和 Claude Code。
- **Cordis 只用在检索服务内部**：多种检索实现（第一版至少两种，如 grep 与一种索引）作为插件，按项目配置装配；管理实现之间的依赖、后台建索引与增量更新任务、切换时的清理。
- 其他平台能力第一版按"能力接缝"思想写成"接口 + 可替换实现 + 平台默认配置 / 项目覆盖"，不使用 Cordis。
- **重新考虑的触发条件**：某项平台能力出现第二个实现，且需要按项目选择或在运行中切换，而普通接口加配置难以满足时，再把它迁到 Cordis 上。

## 理由

- 检索服务是唯一同时满足"在 pi 之外、多实现并存、按项目装配、有长期生命周期和后台任务"的位置。Cordis 的服务注入、依赖声明和可撤销副作用正好对应这些需求。
- 其他位置要么 pi 扩展已能覆盖，要么第一版只有一个实现，用 Cordis 就是为了凑关键词（反目标）。
- 边界清楚，面试时可以讲："循环内用 pi 扩展，平台层多实现能力用 Cordis，第一个用在检索服务。"

## 后果

- 003 中"编排层使用 Cordis 做装配"这条理由不再成立；选择 TypeScript 的其他理由（pi 的 SDK 与扩展、前端）仍然成立，003 不作废。
- 第一版必须至少提供两种检索实现，否则本决定的前提不成立，应改为不引入 Cordis。
- 需要评测各检索实现的效果（找全相关文件的比例、耗时、成本），并如实说明测试所用仓库的规模；单机与公开数据测不到 300GB 级别，不得声称。
- Cordis 的可用性在检索服务开工时验证。
