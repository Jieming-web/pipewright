# 006：首个微调对象是工单理解小模型

- **状态**：已确认
- **日期**：2026-11-08
- **相关**：proposal.md R9、S8 ／ design.md 3.3、3.12

> 本记录确认后不再修改正文。改变决定时，新写一份记录，并把本记录的状态改为"已被 NNN 取代"。

## 背景

作者希望增加本地部署与微调的能力，同时微调必须对应真实问题、有评测数据（反目标）。编排层需要一个本地小模型来理解工单（见 004）。面试中还可能被问到"为什么单独用一个本地模型，而不是让主模型直接读工单"。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 用 agent 执行轨迹微调整个 agent | 直接提升端到端能力 | 长流程、多轮工具调用，任务难；需要大量轨迹并转换格式；大概率要租 GPU；效果只能看端到端成功率，影响因素多 |
| B. 微调工单理解小模型（提取 + 分类） | 输入输出固定，任务清楚；公开 issue 加标注即可；小模型 LoRA 算力需求低；准确率可直接测；就是产品里那个模型 | 对端到端成功率的影响是间接的 |

## pi 的做法

不涉及。pi 不做模型训练。

## 决定

采用方案 B，先微调工单理解小模型。方案 A 以后再定。

- 评测做三方对比：小模型原版、微调后、主模型，比较提取与分类的准确率、成本、延迟。
- 训练数据可由强模型批量标注公开 issue 并人工抽查。
- 测试集必须人工标注，且来自训练数据中没有出现过的仓库。

## 理由

- 任务边界清楚、数据好准备、效果可直接测量，适合作为第一次微调。
- 三方对比用数据回答"为什么单独用本地小模型"：若微调后接近主模型而成本低很多，理由就成立；否则如实记录。

## 后果

- 需要准备标注数据，并决定数据来源（proposal 第 6 节）。
- 用强模型标注训练数据时，若测试集不是人工标注，评测只能说明"小模型模仿强模型的程度"，因此测试集必须人工标注。
- 是否需要租 GPU 取决于小模型的型号，开工时确定。
