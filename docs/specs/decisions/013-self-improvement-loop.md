# 013：自我改进循环（RSI）

## 背景

作者希望把递归自我改进（RSI）融入 coding agent：系统通过执行任务、获取反馈、验证改进，持续优化自身能力组件，形成"执行 → 评估 → 改进 → 再执行"的闭环。coding agent 天然会改代码，而它自身由代码、提示词与配置构成，适合做这件事。关键问题是改进哪一层、工程量与风险是否可控。

## 备选方案

| 层次 | 改进什么 | 工程量与风险 |
|---|---|---|
| 模型层 | 用轨迹反复微调模型 | 很大：每轮需训练、GPU、评测，周期以天计 |
| **系统层** | 提示词补充、skill、路由规则、检索配置、工具与代码 | 中等：评测框架、可修改的配置面、PR 交付、审批流程均已在规范中 |
| 经验层 | 记忆、skill 库 | 已由长期记忆（R13）覆盖 |

系统层内部的可修改范围：

| 档位 | 内容 | 结论 |
|---|---|---|
| 第一档 | skill 文本、提示词补充、路由规则、检索实现选择与参数、经验记忆 | 先做 |
| 第二档 | 工具与扩展代码 | 以后再做，必须沙箱验证并人审 |
| 禁区 | 评测集、判分逻辑、策略服务、权限、审批、工具拦截扩展 | 永远不可修改 |

## pi 的做法

pi 不包含自我改进机制。

## 决定

- 做系统层的自我改进，自主程度为 L2（策略自主）：人设定目标、评估标准与边界，系统自己归因、提出改进、验证，人审批后生效。
- 第一档范围；禁区由代码强制。
- 根因与改进方式对应：知识缺失 → 记忆或检索配置；策略错误 → 提示词补充或路由规则；工具问题、模型能力不足 → 只记录。
- 每轮只改一处，以 PR 提交；开发集前后对比、重复多次；采纳标准同时看成功率与转人工比例、追问次数、成本，并要求其他任务不退步；人审批合并；留出集定期复核。
- 作者手动触发，每轮预算上限，轮数上限与低收益自动停止，改动可按版本回滚，每轮完整记录（含未采纳）。

## 理由

- 系统层所需的零件（评测、可修改配置、PR、审批）已在规范中，只需把它们串成循环，工程量可控（一个任务）。
- 本质上是把项目的 eval-first 开发方式自动化，并有数据可讲。
- 以测试是否通过作为主要评判，比让模型自评更客观；禁区与多指标采纳标准防止"改考卷"和"刷分"。
- 不超过 L2：不做自主探索新环境、不让优化器改进自身、不在循环内自动微调模型。

## 后果
