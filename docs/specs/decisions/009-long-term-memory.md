# 009：长期记忆的写入与召回

- **状态**：已确认
- **日期**：2026-11-08
- **相关**：proposal.md R13、S12 ／ design.md 3.15 ／ 008

> 本记录确认后不再修改正文。改变决定时，新写一份记录，并把本记录的状态改为"已被 NNN 取代"。

## 背景

平台需要让 agent 记住跨任务、值得复用的知识，避免员工反复纠正同一件事。与单用户命令行工具不同，本平台多用户、记忆可共享、输入（工单、仓库、粘贴内容）不可信，一条有毒的记忆会影响整个团队；因此防线不能只靠提示词。

参考的公开来源：Claude Code 公开文档中的记忆机制（`CLAUDE.md`、按主题文件加索引、后台提取）、mem0（Apache 2.0，候选提取后与已有记忆比对决定新增/更新/删除/不变）、OpenHands 与 Gemini CLI 对"指令文件"和"记忆"的区分、PACE（Wei et al., ACL 2026）的多粒度与按需展开。

## 备选方案

存什么：

| 方案 | 内容 | 问题 |
|---|---|---|
| A. 只存推不出来的背景，不存修法 | 背景、原因、资料位置、经验、个人偏好 | 需要历史检索兜底修法 |
| B. A + 修 Bug 的方法 | 额外存经过验证的根因与修法 | 记忆量大、易过期；修法本可从提交历史检索 |

怎么生效：

| 方案 | 问题 |
|---|---|
| 全部需审批后生效 | 审批积压，批准前员工仍要重复纠正，核心价值打折 |
| 全部自动生效 | 中毒风险高 |
| 按范围区分 + 提出者先试用 + 批量审批 | 兼顾及时性与安全 |

## pi 的做法

pi 没有长期记忆，只有静态的上下文文件（`AGENTS.md` 等），不会从任务中提取经验，也没有按相关性召回。

## 决定

- **存什么**：方案 A。项目和团队范围的"要求"走规则（008）；代码修法交给提交历史检索（R12，T7 第一版提供）。
- **依据可核对**：依据必须指向真实存在的人话（消息 ID + 原文子串校验）或平台记录的执行状态（一败一成）；疑似粘贴内容、工单、仓库内容、工具输出文字、PR 评审意见不能作为依据。
- **写入与生效分离**：模型通过 `memory_propose` 只能产生候选；代码检查后，个人偏好由本人再点一次确认生效；项目和团队内容先对提出者试用，审批后扩大，试用 30 天未批自动过期；审批以批量清单形式处理。
- **被结果验证的经验**：只收环境、构建、测试方面的坑；先对本人试用，多会话重复出现或经人确认后才进入项目审批。
- **触发**：主 agent 主动提议；每轮结束经本地小模型前置过滤后由后台任务提取（游标存数据库、幂等、合并）。
- **召回**：第一版全量标题与描述 + `memory_expand` 按需展开，以追加消息方式注入以保护提示词缓存；按当前发消息的人召回个人偏好，多人会话不注入个人偏好；超过阈值后再启用分层挑选（借鉴 PACE）。
- **维护**：有效期、90 天复核、使用中更正；第三版加入文件变化信号、定期整理（只产出提议）、升级为规则的 PR。
- **分三版实施**，见 tasks.md。

## 理由

- 只存推不出来的背景，记忆量小，过期与中毒风险低；修法有提交历史可查。
- 防线由代码执行（依据核对、原文子串、指令过滤、权限隔离），不只依赖提示词。
- 提出者先试用，避免"批准前还要重复说"；批量审批避免审批人被逐条推送淹没。
- 第一版召回不引入向量与小模型精选，与预期规模（每项目每年几十条）相符。

## 后果

- 依赖检索服务提供提交历史检索与文档比对。
- 依赖平台审批流程与编排层本地小模型。
- 需核实 pi 扩展的上下文钩子能否只追加。
- 评测（S12）：重复纠正次数、中毒测试、转述准确率在第一版就做。
- 简历可讲：写入与生效分离、来源可核对、策略/规则/记忆三层分离（防止 agent 被投毒）。
