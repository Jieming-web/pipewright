# 010：跨仓库只读

- **状态**：已确认
- **日期**：2026-11-08
- **相关**：proposal.md R10 ／ design.md 3.10、3.13、3.16 ／ tasks.md T7、T10

> 本记录确认后不再修改正文。改变决定时，新写一份记录，并把本记录的状态改为"已被 NNN 取代"。

## 背景

企业里一个请求往往经过多个服务，排查时要沿调用链跨几个仓库查看代码。原设计中一个会话只绑定一个仓库，无法回答"页面提示库存不足，是前端自己判断的还是库存服务返回的"这类问题。

## 备选方案

| 方案 | 场景 | 难点 |
|---|---|---|
| A. 沿调用链跨几个相关仓库 | 一个请求一路经过了哪里、问题可能出在哪一层，交付带代码证据的调用链 | 仓库之间的调用关系；多仓库的权限与版本 |
| B. 全公司范围代码搜索 | 所有命中在哪里（如还有谁在用某个废弃库） | 规模大、逐仓库权限、要说明搜索覆盖面与索引新旧 |

实现上的子选择：

| 选择 | 采用 | 理由 |
|---|---|---|
| 全部检出到沙箱 vs 索引 + 按需读取 | 索引 + 按需读取，需要运行时再检出 | 只读问答不需要完整检出，成本低 |
| 自动发现依赖 vs 用户显式选仓 | 显式选仓 | 省掉依赖发现的复杂度；扩大范围由用户决定，符合"从最小范围开始，扩大须确认" |
| 跨仓库修改 | 不做 | 多个 PR 需要一起合并或回滚，难度高；拆成单仓库任务 |

## pi 的做法

pi 在单个工作目录中运行，内置工具只能读写本地文件系统，没有多仓库或权限的概念。

## 决定

- 第一版做方案 A，只读，覆盖 `code_qa` 与 `bug_triage`。
- 用户显式选择仓库，编排层逐个检查权限；pi 需要其他仓库时只能建议，由用户加入，写入审计。
- 检索服务提供按（仓库、路径、版本）读文件的 MCP 工具；需要运行测试时再检出对应仓库。
- 会话中每个仓库固定分支与提交，证据写成"仓库@提交:文件:行号"；找不到下一跳时标为"只验证到这里"。
- 修改类任务一次只改一个仓库；多仓库修改拆成多个单仓库任务。
- 方案 B 以后再定。

## 理由

- A 最贴近代码问答与 Bug 排查，交付物明确、可用评测检验。
- 不全部检出、显式选仓，让第一版的复杂度可控。
- 扩大范围由用户决定，agent 不能自行扩大可见范围，即使仓库内容诱导也只能形成建议。

## 后果

- 会话的数据模型从"绑定一个仓库"改为"绑定一组仓库"，每个仓库带分支、提交、读写属性、加入人与理由。
- 召回记忆、注入规则（各仓库基准分支的 `AGENTS.md`，注明来源）都按这组仓库进行。
- 需要评测调用链完整度，以及显式选仓打断排查的频率；若打断过于频繁，再考虑自动发现依赖。
