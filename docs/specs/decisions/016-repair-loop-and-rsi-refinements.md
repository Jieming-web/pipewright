## 背景

loop engineering 原定第二版再讨论（2026-11-09）。2026-11-20，作者带来一篇生产 RCA Agent 的实践文章（Loop Engineering + RSI，作者分段提供，未公开，这里只引用其中的做法）。文章的核心做法：

- 调查结论、修复生效、方法改进三件事分开验收，不共用一个"完成"状态；
- 能用规则判定的检查交给控制器，模型只负责提出假设和选择检查；
- 修复用持久状态机推进，批准绑定在具体改动上；
- 改进按"首次失效位置"决定改 Memory 还是 Harness，候选冻结后在留出集评估，发布后回读实际加载的版本。

对照 ForgePilot 后发现两点：

- **中层循环是空白**：单个任务内"pi 尝试 → 判定 → 带着反馈重跑 → 停下或转人"这一层，规范里没有。bug_fix 只写了"修改、测试并产出 diff"，做没做好全靠模型自觉。
- **RSI（013）骨架已有，但缺几处**：反馈核实、失效位置分类、防刷分的留出集设计、运行快照。

三层循环的关系：内层是 pi 的模型 ↔ 工具循环（pi 自带）；中层是单个任务的修复循环（本记录）；外层是 RSI（013）。

## 约束

## 决定

### 1. bug 修复循环（新任务 T23，design 3.18）

```
排查：agent 写复现测试，控制器在基准提交上确认它失败（这就是证据）；测试与失败输出存为平台记录
→ 最小修复方案 → 确认（批准绑定这份方案）
→ 新沙箱恢复复现测试并再次确认失败 → 修改 → 判定（由控制器执行）：复现测试通过，原有测试不退步，diff 不超出确认范围
    ├ diff 超出范围 → 立即回到确认，计为一次尝试（防止无限往返）
    ├ 未通过 → 把失败输出交还 agent 再改，默认最多 3 次尝试（含第一次）
    └ 轮数用完 / 预算用完 / 连续两轮失败特征相同（无进展）→ NEEDS_HUMAN，附证据，工单保留
→ 通过 → 创建 PR（幂等）→ 人工合并
```

- 判定器是规则，不是模型。"没跑通测试就宣称修好"由判定器直接拦下，不交给 RSI 去学。
- 原有测试用项目配置中的测试命令。评测中隐藏测试（测试补丁）不进入修复循环的容器，只在交付后由评测框架单独运行。
- 无法用测试复现的 bug（作者定）：先追问一次复现条件；仍写不出失败的复现测试，就只交付排查结论，转 `NEEDS_HUMAN`，不自动修改代码。理由：判定器缺了复现测试，“修好了”就没有证据。
- feature_request 可复用这个循环（判定器换成先写好的验收测试），本期不验收。

### 2. 文章做法的取舍

**值得做**（基本都是规则，代价小）：

1. 修复循环（上一节）。
2. **运行快照**：每次运行记录 pi 与模型版本、实际注入的规则文件（仓库、路径、来源提交、哈希），以及评测配置版本。由引擎从加载器回读实际加载的内容，不照抄输入参数。
3. **证据三态**：自研的检索与读文件工具区分"完整 / 部分或截断 / 失败"，不把三者都返回成空结果。
4. **批准绑定方案**：实际 diff 超出已批准方案的范围（如改动未列出的文件）时，重新确认。
5. **PR 幂等**：用稳定的键去重，重试前先查是否已创建。
6. **排查结论三态**：每条结论标为"有证据支持 / 有证据否定 / 证据不足"。没找到证据不等于有反证。
7. **RSI 反馈先核实**：对照原始轨迹核实后，按"最早在哪一环失效"分类，由模型提出建议、作者拍板。模型自评或赞同不算核实。
8. **冻结失败基线，防刷分**：改动前冻结错误、证据与出错步骤；开发集与留出集尽量使用不同仓库，同仓库的题单独统计并报告占比；转人工或 `NEEDS_HUMAN` 计为未解决，不能靠转人工降低错误数；参考答案不得进入提示词、skill 或记忆（提交前扫描候选改动）。

**简化着做**：

- 每轮 1–2 个候选，由作者挑选；不做多目标候选搜索。
- 经验记忆只增加三个字段：适用条件、已知反例、失效条件。
- 报告口径：只说"这一类失败修好了，留出集上没有超出波动的退步"，不写"成功率提升 X%"。几十道题时，一道题就占 2–3%。

**不做**：

- 元改进（见上表）。
- RSI 修改工具代码：仍属 013 的第二档。工具有 bug 时只记录，由作者手动修。
- 因果推断与分母比例统计（DoWhy、CausalImpact 等）：没有生产流量，评测题有隐藏测试直接判定。
- 影子运行、灰度、线上验收窗口、自动触发：没有生产环境，RSI 由作者手动触发（013）。
- 独立的不变量与故障注入测试集：只在检索工具的单元测试里覆盖截断和失败两种情况（第 3 条）。
- AIOpsLab 一类隔离环境基准：SWE-bench 的 Docker 环境就是我们的隔离环境。

### 3. 与 013 的关系

013 的决定全部保留：L2 自主程度、第一档范围、禁区、每轮只改一处、人审批、手动触发、预算与停止条件。禁区扩大：修复循环的判定器及其配置（轮数上限、测试命令、范围规则），以及 RSI 自身的归因、提案与验证流程（含其提示词、skill 与代码）也不可修改——否则优化器可以经第一档（skill、提示词、配置）绕过“不做元改进”。本记录只补充反馈核实、失效位置分类、留出集设计、运行快照与报告口径，以及中层修复循环。

## 理由

- 修复循环是 loop engineering 的核心，也是 bug_fix 质量的直接来源；判定器全是规则，可测、便宜。
- RSI 的归因依赖修复循环留下的逐轮记录和运行快照。没有快照，就分不清某次失败来自哪个版本。
- 取舍按"一人审核、几十道题"的规模做：能写成规则的写成规则，需要大样本或生产流量的不做。
