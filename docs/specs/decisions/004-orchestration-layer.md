# 004：编排层用本地小模型理解、规则路由

- **状态**：已确认
- **日期**：2026-11-08
- **相关**：proposal.md R11、S10 ／ design.md 3.3–3.7

> 本记录确认后不再修改正文。改变决定时，新写一份记录，并把本记录的状态改为"已被 NNN 取代"。

## 背景

企业里的需求往往以工单形式到来：描述、评论、附件、关联单混在一起，信息常常不全。直接交给 agent，它可能在信息不足时硬修，或用错误的方式处理（例如该排查的直接改代码）。需要一层在 agent 之上把需求整理成可执行任务，并决定怎么处理。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 不加这一层，工单直接交给 agent | 最简单 | 信息不足时浪费 token、交出看似修好实则没修对的 PR；处理方式无法按项目规则控制 |
| B. 让主模型（agent 本身）先读工单再决定怎么做 | 理解能力强 | 成本高；决定由模型做出，难以保证确定性和权限边界 |
| C. 本地小模型理解 + 确定性规则路由 | 便宜、快、数据不出部署方；路由可审计、可配置；分类与权限分离 | 小模型可能理解错；需要定义类别、校验输出、设计等待状态 |

## pi 的做法

pi 没有这一层。它直接接收用户输入并开始 agent loop，没有工单理解、分类路由或审批。

## 决定

采用方案 C：

- 本地小模型只负责理解：提取固定字段并附原文出处，给出分类建议。
- 编排层负责确定性部分：校验、请求补充、组装上下文、按项目路由规则在权限范围内路由、推进任务状态机。
- 编排层只发起和串联，审批、权限、取消、预算由各自的服务负责。
- 类别：`code_qa`、`bug_triage`、`bug_fix`、`feature_request`、`change_review`、`support_request`（`access_request`、`environment_issue`）、`unknown`。路由只用"处理类别"，不用根因。
- 从权限最小的类别开始，升级必须确认；所有等待共用一套可恢复的状态机制；超时结束本次自动处理、保留工单。
- **模型分类不能代替权限判断；"改分类"和"授权执行"是两个操作。**
- 本地模型不可用时跳过预处理，原始工单直接交给引擎并标记。

## 理由

- 作者希望增加本地部署和微调的能力，工单理解是一个边界清楚、可微调、可直接测准确率的任务（见 006）。
- 把"理解"和"决定"分开，路由结果可配置、可审计，不受工单中注入内容的影响。
- 从最小权限开始、升级要确认，符合企业对 agent 的安全要求。

## 后果

- 需要人工标注一批公开 issue 作为分类与提取的评测集。
- 需要用评测证明这一层有用（S10）：2×2 对比、分类与提取准确率、小模型与主模型对比。若数据显示无用，如实记录。
- 新增多个契约：工单理解输出、路由规则、任务状态、审批。
