# 003：后端与前端以 TypeScript 为主

- **状态**：已确认
- **日期**：2026-11-08

## 背景

002 决定 Python 为主、pi 扩展只写一层 TypeScript 薄桥。之后的讨论新增了编排层：它要按任务类型和项目要求选择引擎、检索器和执行工具，并完成装配。作者希望用 Cordis（一个 TypeScript 插件框架，出自 Koishi，主打依赖声明与热插拔）做装配。此外，pi 的扩展和 SDK 只支持 TypeScript，工作台前端也是 React + TypeScript。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 维持 002（Python 为主 + TS 薄桥） | 作者要学的集中在 Python | 编排层若用 Cordis 就必须是 TS，与 002 冲突；与 pi 之间多一层进程间通信 |
| B. 后端与前端都用 TS，微调和评测用 Python | 与 pi、Cordis、前端同一门语言；可直接用 pi SDK 和扩展 API，不需要薄桥 | 推翻 002；国内 AI 后端主流是 Python；作者要学 Node 后端 |
| C. 编排层用 TS，其余后端仍用 Python | 只在需要 Cordis 的地方用 TS | 后端拆成两门语言，跨语言调试，模块边界更多 |

## pi 的做法

pi 用 TypeScript 编写，提供 TypeScript SDK 供进程内嵌入，扩展也只能用 TypeScript 编写。

## 决定

采用方案 B：

- 后端（编排层、引擎适配器、会话服务、策略服务、审批、沙箱管理）与工作台前端都用 TypeScript。
- 微调用 Python；评测大概率用 Python（T2 开工时确定）。

## 理由

- 编排层使用 Cordis 做装配，Cordis 是 TypeScript 框架。
- 与 pi 同一门语言，可以直接使用 pi 的 SDK 和扩展 API，不再需要 002 中的 RPC + 薄桥结构。
- 后端只用一门语言，避免方案 C 的跨语言拆分。

## 后果

- 002 作废，状态改为"已被 003 取代"。
- 作者要学 Node / TypeScript 后端，而不是 Python 后端。
- 微调和评测仍是 Python，项目中存在两门语言，边界在"训练与评测"和"产品后端"之间。
- 引擎是否放在沙箱容器内仍需决定（design.md 第 8 节第一条）；若放在容器内，扩展询问策略服务仍有一次跨容器通信，002 中关于"不可用即拒绝、记录耗时、快速通道"的要求继续适用。
- Cordis 的可行性在开工时验证。
