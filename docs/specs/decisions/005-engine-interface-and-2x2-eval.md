# 005：统一引擎接口与 2×2 对照

- **状态**：已确认
- **日期**：2026-11-08
- **相关**：proposal.md R1、S10 ／ design.md 第 1 节、3.11

> 本记录确认后不再修改正文。改变决定时，新写一份记录，并把本记录的状态改为"已被 NNN 取代"。

## 背景

作者的架构图中，执行层写着"AgentLoop · 默认 Pi"和"统一接口 · 实现可替换"。作者希望 pi 是默认引擎，并用 Claude Code 作对照组。顾虑是：Claude Code 本身比 pi 强，放进同一个编排层后，结果会被引擎能力干扰，说明不了编排层的价值。

## 备选方案

| 方案 | 能回答的问题 | 缺点 |
|---|---|---|
| A. 编排层只作用于 pi，比较有无编排层 | 编排层对 pi 有没有用 | 回答不了"比通用工具好不好"，也不知道对强引擎是否有用 |
| B. Claude Code 单独运行 vs pi + 编排层 | 平台比通用工具好不好 | 引擎、模型、编排层三个变量混在一起 |
| C. 2×2：pi / Claude Code × 有无编排层 | 编排层对每个引擎的提升（同一引擎内比较，引擎强弱相互抵消）；编排层的价值是否依赖引擎；平台与通用工具的对比 | 要写两个适配器，评测次数翻倍 |

## pi 的做法

pi 不涉及多引擎。它是一个单一的 Harness。

## 决定

采用方案 C：

- 编排层只依赖本项目定义的统一引擎接口；pi 和 Claude Code 各有一个适配器。
- pi 是产品的默认引擎；Claude Code 只在公开数据的评测中使用，不进入产品（会把代码发送到外部服务，违反"数据不出部署方"）。
- 是否再加一组"pi + Claude 模型"来分离引擎与模型的影响，定评测方案时决定。

## 理由

- 每组对比只改变一个变量，"Claude Code 更强"不会干扰"编排层有没有用"的结论。
- 若编排层对 Claude Code 也有提升，说明它的价值不依赖引擎，是最有说服力的结果。
- 统一接口让服务层不绑定 pi 的内部细节，以后升级或替换引擎影响更小。

## 后果

- 需要定义 `contracts/engine.md`，并核实 Claude Code（Claude Agent SDK）是否提供工具执行前拦截等能力；不同引擎能力不一致时，接口按最小公共能力设计，差异在报告中注明。
- 评测成本增加。
- 引擎差异与模型差异（Claude Code 用 Claude 模型，pi 用 Qwen）混在一起，报告中必须注明。
