## 背景

项目需要客观、可复现的评测（R2），覆盖端到端修复、工单分类与提取、检索、各工作台模式、跨仓库、中毒防护，并为工单理解小模型的微调准备数据。项目没有企业数据，只能使用公开数据或合成数据。作者倾向使用大量真实仓库的 issue。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 全部自建小仓库 | 无污染、可控 | 规模小，与真实场景差距大，无法和社区比较 |
| B. 只用 SWE-bench 系列 | 真实 issue、测试判定客观、有现成 Docker 环境 | 只覆盖 `bug_fix`（及少量功能）；老题可能被模型见过；以 Python 为主；镜像以 x86 为主 |
| C. SWE-bench 系列为主，其余类别合成，测试集用真实数据人工标注 | 兼顾真实性、覆盖面与可验证性 | 合成数据有分布偏差、答案可能出错、偏向生成模型等风险，需要规矩约束 |

## pi 的做法

不涉及。

## 决定

采用方案 C：

- 端到端开发集：SWE-bench Verified 子集；留出集：SWE-bench-Live 中训练截止日期之后的新任务（Live 停更则用 SWE-rebench 按月划分）。
- 工单分类与提取的测试集：同一批仓库的原始 issue，人工标注；微调训练集来自其他仓库，强模型标注加人工抽查，再加合成工单。
- 其余类别与中毒测试使用合成数据，借鉴 SWE-smith"先造答案、再出题"的方式，并遵守 design 3.11 的合成规矩（自动验证、人工抽查、生成模型与被评测模型分开、报告注明合成）。
- 防污染：留出集只用截止日期之后的题；评测中检索只能看到任务基准版本之前的内容；PR 描述与评审意见只能看到 issue 创建时已存在的内容。
- 运行环境：Mac 只跑冒烟测试，正式评测租 x86 云服务器（只需 CPU），微调期间可与 GPU 服务器合用。

## 理由

- SWE-bench 系列提供真实 issue 与客观测试判定，并有现成环境，适合端到端评测。
- 按月更新的数据集让留出集可以只用模型没见过的题，解决"见过题目"的问题；开发集的偏差在相对比较中大致抵消，但最终结论以留出集为准。
- 本项目的检索服务包含提交历史，若不做时间截断，修复提交会直接泄露答案，这是本设计特有的风险。
- "先造答案、再出题"让合成数据的标准答案可以由代码核对，不依赖生成模型的判断。
- 镜像架构问题与 GPU 无关，用只需 CPU 的 x86 云服务器即可解决。

## 后果

- T2 开工时需确定开发集规模、所用 Qwen 的训练截止日期与留出集起始月份、生成合成任务所用的模型。
- 评测框架需支持远程 Docker 主机与检索的时间截断。
- 需要人工标注分类与提取测试集。
- 报告中不引用第三方排行榜分数，并注明开发集分数可能偏高、哪些结果来自合成数据。
