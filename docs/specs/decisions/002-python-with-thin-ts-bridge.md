# 002：Python 为主，pi 扩展只写 TypeScript 薄桥

- **状态**：已确认
- **日期**：2026-11-05
- **相关**：proposal.md 第 5 节（语言）、R1、R6 ／ design.md 第 1、2 节、3.2

## 背景

复用 pi 之后（见 001），本项目要接入 pi 的地方有两类：

- 必须挂进 pi 进程的：工具执行前的拦截（权限、确认）、注册新工具（子 agent、企业工具）。pi 的扩展和 SDK 只支持 TypeScript / Node.js。
- 放在哪一边都可以的：服务层、沙箱、评测、微调、可观测。其中评测和微调的生态基本在 Python。

所以 Python 一定会有，要决定的是 TypeScript 写多少。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. Python 服务 + TS 扩展承载逻辑 | 与 pi 交互的逻辑都在 pi 进程内，没有额外通信 | 逻辑分散在两门语言；作者要用两门语言写核心代码；跨语言调试 |
| B. 全部改用 TypeScript（服务层用 Node，进程内调用 pi SDK） | 与 pi 同语言，可直接用 SDK | 评测和微调仍需 Python；国内 AI 后端主流是 Python；作者要改学 Node 后端 |
| C. Python 为主，TS 只写一层薄桥 | 作者要学的集中在 Python；策略在 pi 进程外，agent 被诱导也改不了策略；TS 代码量小（估计一两百行，不含业务逻辑） | 每次工具调用多一次进程间通信；策略服务成为单点，需要处理不可用 |

## pi 的做法

pi 本身用 TypeScript 编写，官方建议非 Node 宿主通过 RPC 或 JSON 模式以子进程方式集成；扩展在 pi 进程内运行，与 pi 拥有相同的操作系统权限。

## 决定

采用方案 C：

- 服务层、策略服务、子 agent 服务、skill 管理、评测、微调用 Python。
- pi 扩展只写一层 TypeScript 薄桥：`tool_call` 前把调用转给 Python 策略服务并执行其决定；本项目注册的工具在执行时转给 Python；确认弹窗原样转发。薄桥不含策略判断和业务逻辑。
- 子 agent 由 Python 另起一个只读的 pi 进程实现。

附带要求：

1. **不可用即拒绝**：策略服务连不上或超时，一律拒绝执行。
2. **单独记录转发耗时**：用评测的真实数据判断这一跳是否影响延迟。
3. **快速通道作为后手**：数据表明这一跳显著拖慢任务时，把最简单、最常见的判断（如只读工具直接放行）下沉到薄桥本地完成。

## 理由

- 时间紧（11 月底），作者前后端基础偏弱，把要学的集中在一门语言上最省时间。
- 评测和微调无论如何都要用 Python。
- 策略与执行分离是一个可讲的安全设计：策略决策点在 agent 进程之外。
- 作者关心延迟。按数量级估算，本机或内网一次转发约 0.1 毫秒到几毫秒，而模型推理一轮约 1–30 秒，一个任务总耗时以分钟计，转发占比预计不到千分之一。这是估算，以评测实测为准。
- 原先选 Python 的理由之一"避免看起来像照抄 pi"在公开复用 pi 之后不再成立，本决定不依赖这条理由。

## 后果

- 需要定义薄桥与 Python 服务之间的接口（`contracts/bridge.md`），包括超时与失败语义。
- 策略服务的可用性直接影响所有工具调用，要有超时、拒绝和监控。
- 工作台前端另用 React + TypeScript，不属于本决定的范围（前端以展示产品完整性为目的，主要由 AI 辅助完成，见 proposal 3.2）。
