# 001：复用 pi 作为 Agent Harness

- **状态**：已确认
- **日期**：2026-11-05
- **相关**：proposal.md 第 1 节、R1、R5、3.2 ／ design.md 第 1、2 节

> 本记录确认后不再修改正文。改变决定时，新写一份记录，并把本记录的状态改为"已被 NNN 取代"。

## 背景

项目最初的设计是用 Python 从 0 到 1 自研 Agent Harness（agent loop、read/write/edit/bash 工具、上下文压缩等），参考 pi 的设计思想但不复用代码。

讨论中出现两个新约束：

1. 作者简历上已经有 Agent Harness 的经验（私募客服 Agent 的 Harness 重构）。再自研一遍，面试官看到的是同一种能力。
2. 作者要投寒假实习，2026 年 11 月底需要一个能写进简历的版本。自研 Harness 会占掉前几周。

同时，产品定位改为面向企业内部部署，要求能使用本地模型（代码和数据不出部署方）。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 自研 Harness | 每个设计都亲手做过，能讲出取舍并有自己的数据 | 与简历已有经验重复；占用 11 月底前的大部分时间；大概率不如成熟 agent |
| B. 复用 pi | MIT 许可；能接本地模型（`models.json` 配 OpenAI 兼容地址）；有 RPC 模式，可被 Python 驱动；有扩展机制（`tool_call` 钩子可拦截、注册新工具）；时间可以集中在 Harness 之上 | 扩展只能用 TypeScript；pi 没有权限系统、不内置子 agent、只讲单会话，这些要自己做；依赖外部项目的演进 |
| C. 复用其他框架（如 Claude Agent SDK、OpenAI Agents SDK） | 生态成熟 | 部分框架与特定厂商模型绑定较紧，是否满足"本地模型"前提需逐个核实；作者已以 pi 为参考 |
| D. 读一周 pi 源码代替自研 | 能讲清成熟 Harness 的做法 | 只能转述别人的取舍，没有自己的数据；不产生可交付物 |

## pi 的做法

pi 是一个刻意保持极简的 Harness：

- 自带 agent loop、内置工具、上下文压缩（插入摘要替代旧消息）、skill 按需加载（系统提示词里只列名称、描述和路径，需要时由模型读取 `SKILL.md`）。
- 据 Pi 1.0（2026-10-01）的发布报道，已内置 MCP 支持（待对照官方文档核实）。
- 刻意不内置子 agent 和计划模式，建议需要的人安装扩展包。
- 没有权限系统，工具以启动 pi 的进程的操作系统权限运行；官方建议用容器等方式隔离。
- 提供交互、打印 / JSON、RPC、TypeScript SDK 四种使用方式。

## 决定

采用方案 B：复用 pi 作为 Harness，以未修改的依赖形式使用。

取舍规则：**pi 自带的能力不重做；pi 不带的，由本项目实现。** 只省略自研 Harness 这一部分，其余范围全部保留。据此：

- 不做：agent loop、内置工具、上下文压缩、skill 加载机制、MCP 客户端。
- 要做：权限与审计、子 agent、skill 的分发 / 权限 / 版本 / 效果评测、MCP 工具的风险等级、多会话服务、沙箱、评测、可观测、本地部署与微调、企业工作台。

## 理由

- 避免与简历已有的 Harness 经验重复，把时间花在面试中能形成新信号的部分。
- pi 满足"本地模型"前提，并提供 RPC 与扩展两个集成点，能在不改源码的情况下接入本项目的能力。
- pi 缺的正好是企业场景需要的（权限、多会话、隔离），这些成为本项目的主要内容。

## 后果

- 原 proposal 中"用 Python 从 0 到 1 自研 Harness"及相关任务（最小 agent loop、编辑工具、上下文管理）作废，`tasks.md` 需要重写。
- 原反目标"看起来像照着 pi 源码翻写"不再适用，改为"说不清哪些是 pi 提供的、哪些是本项目做的"。
- 需要写一部分 TypeScript（见 002）。
- 依赖 pi 的版本演进：RPC 事件格式或扩展 API 变化时，需要调整 RPC 宿主适配和薄桥。服务层基于本项目自己的事件协议，以缩小影响范围。
- 面试中要能清楚划分 pi 提供的能力和本项目实现的能力。
