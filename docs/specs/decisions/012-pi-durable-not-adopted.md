# 012：不采用 pi-durable，借鉴其设计

- **状态**：已确认
- **日期**：2026-11-08
- **相关**：proposal.md R3、S5 ／ design.md 3.5、3.10 ／ tasks.md T3、T14

> 本记录确认后不再修改正文。改变决定时，新写一份记录，并把本记录的状态改为"已被 NNN 取代"。

## 背景

R3 要求服务器崩溃或重启后，正在执行的任务能继续（S5，T14）。pi 仓库中有一个 `@earendil-works/pi-durable` 包，是一个持久化的 agent harness，可能与此重叠。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 引擎仍用 pi coding-agent，T14 自己实现，借鉴 pi-durable 的设计 | 引擎稳定；平台层崩溃恢复是作者"真正学会后端"的核心 | 引擎内部的断点续跑需自己用 pi 会话文件与平台检查点实现 |
| B. 引擎换成 pi-durable | 引擎内部持久化现成 | 标注为实验性质，"API changes without notice"；是与 pi coding-agent 平行的另一套运行时，需重新验证编码工具、扩展、上下文文件等；推翻大量已有设计 |
| C. 以后通过统一引擎接口作为第二个基于 pi 的引擎接入 | 可做对比 | 当前不稳定 |

## pi 的做法

pi-durable（README 所述）：所有变化先原子提交到存储再展示；进程崩溃后重新打开存储从断点继续；崩溃时正在执行的工具调用，只有声明 `replay: "safe"` 的才重跑，其余返回 `interrupted` 错误结果；被崩溃打断达到 `restartLimit`（默认 5）的任务终止，防止崩溃循环；相同 `requestId` 的重复提交返回同一提交；任务可持久化地睡眠，重启后到点唤醒；支持只读打开；任务与阶段带遥测。pi coding-agent 目前不依赖 pi-durable。

## 决定

采用方案 A，并把方案 C 作为以后的选项：

- T14 由本项目实现（API 与 worker 拆分、任务租约、检查点、Redis 限流与配额）。
- 借鉴三点：
  1. 工具风险等级表增加"能否安全重跑"：只读类崩溃后直接重跑，有副作用的返回"中断"错误、不自动重跑。
  2. 崩溃循环保护：同一任务被崩溃打断达到上限（默认 5 次）即终止并报告。
  3. 等待与过期使用持久化的定时唤醒，由调度器到点处理。
- **重新评估的触发条件**：pi-durable 脱离实验状态，或 pi coding-agent 改为基于它。届时通过统一引擎接口作为第二个基于 pi 的引擎接入并对比。

## 理由

- pi-durable 只解决引擎内部的持久化，平台层（多 worker 领取、租约、限流配额）仍需自己做，换引擎不能省掉 T14 的主要工作。
- 实验性质的 API 不适合作为产品的默认引擎。
- 它的若干设计（可安全重跑声明、崩溃循环保护、持久化唤醒）补上了我们原设计的空白。

## 后果

- T3 的工具风险等级表需要声明"能否安全重跑"。
- T14 增加崩溃循环保护与持久化唤醒的验收标准。
- 面试中可以讲清：引擎层持久化与平台层崩溃恢复的区别，以及为什么借鉴而不采用。
