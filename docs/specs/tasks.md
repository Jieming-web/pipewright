## T1：接入 pi 与本地模型

- **目标**：Python 服务能驱动 pi 完成任务，模型既可以是本地部署的开源模型，也可以是外部 API。
- **对应需求**：R1、R9（本地模型接入部分）
- **前置依赖**：无
- **输入**：pi（未修改的依赖）
- **输出**：RPC 宿主适配（Python）、本项目事件协议初版、pi 的模型配置、`tests/fixtures/` 下的小型 Python 仓库
- **验收标准**：
  1. Python 以 RPC 模式启动 pi 子进程，发送一条任务，收到流式事件，并能正确判断任务已结束（不会在 pi 还要继续时提前结束）。
  2. pi 的事件被转换成本项目的事件协议；协议写入 `contracts/agent-events.md`，包含与 pi RPC 事件的对应关系和序号规则。转换逻辑有单元测试（使用录制的 pi 事件，不调用真实模型）。
  3. pi 通过 `models.json` 使用在 Mac 本地部署的 Qwen 完成一个任务；切换到外部 API 只改配置、不改代码。
  4. 在 `tests/fixtures/` 的小仓库上，对 5 个"某函数在哪里被调用"的问题：用外部模型全部答对；用本地模型的结果如实记录。两者都写进实现说明。
  5. 宿主能取消正在运行的任务，pi 子进程能被正确清理（测试）。
  6. pi 以锁定版本的依赖形式引入，没有修改或 fork 其源码（S3）。
- **是否需要评测**：否
- **所需环境**：Node.js ≥ 22.19；pi；Mac 上的本地推理工具（如 Ollama）与一个 Qwen 模型；外部模型 API key
- **计划**：

## T2：评测框架 v1 与基线

- **目标**：建立之后每一项改动的"尺子"，并给出外部模型与本地模型的基线。
- **对应需求**：R2、R4、R9（本地模型基线）
- **前置依赖**：T1
- **输入**：T1 的 RPC 宿主适配
- **输出**：评测框架、Docker 执行器、任务集 v1、基线报告
- **验收标准**：
  1. 任务集的来源和规模在开工前确定（proposal 第 6 节），分为开发集和留出集，并标注版本；报告写明数据污染如何检查。
  2. 一条命令跑完整个任务集，输出成功率（均值与波动）、token、轮数、耗时、失败类型，并保存每个任务的完整执行轨迹。
  3. 每个任务在独立的 Docker 容器中、使用独立的仓库副本运行；agent 的命令不在宿主机上直接执行。
  4. 评测中的确认策略写进配置：危险命令自动拒绝，沙箱内的普通命令自动放行。
  5. 运行前输出预计花费，运行后记录实际花费。
  6. 产出基线报告，写进 `docs/evals/`：至少包含外部强模型和本地模型两组（S8 的第一部分）。
- **是否需要评测**：是，产出基线
- **所需环境**：Docker；模型 API key；本地模型；确定对照用的强模型；确定任务来源

## T3：权限、确认与审计

- **目标**：补上 pi 没有的权限系统，策略判断在 pi 进程之外。
- **对应需求**：R5（MCP 工具风险等级）、R6
- **前置依赖**：T2
- **输入**：T1 的 RPC 宿主适配、T2 的评测框架
- **输出**：TS 薄桥（pi 扩展）、策略服务、审计记录、工具风险等级表
- **验收标准**：
  1. TS 薄桥在 `tool_call` 前把调用转给 Python 策略服务，并执行其决定（放行、拦截并返回原因、需要确认）；薄桥不含策略判断。接口写入 `contracts/bridge.md`，包括超时与失败语义。
  2. 策略服务按风险等级决定放行、确认或禁止。风险等级表写入 `contracts/tools.md`，覆盖 pi 内置工具和已接入的 MCP 工具。
  3. 策略服务连不上或超时时，工具调用一律被拒绝（测试）。
  4. 需要确认时，确认请求经 RPC 发给宿主，宿主回答后 pi 继续或收到拒绝原因；确认有超时，超时按拒绝处理（测试）。
  5. 每次策略决定和确认都写入审计记录：时间、会话、工具、参数摘要、决定、由谁确认。
  6. 桥接转发这一跳的耗时单独记录；跑一次评测，报告这一跳在任务总耗时中的占比。
  7. 开启权限策略后重跑评测，与 T2 基线对比，变化如实记录。
- **是否需要评测**：是，对比 T2 基线
- **所需环境**：同 T2
- **计划**：

## T4：多用户会话服务 v1

- **目标**：把 pi 包进多用户的会话服务。
- **对应需求**：R3、R6
- **前置依赖**：T3
- **输入**：T1 的事件协议、T3 的策略服务
- **输出**：FastAPI 会话服务、PostgreSQL 事件存储、SSE 推送
- **验收标准**：
  1. API key 鉴权；会话绑定用户、仓库和模式（对话、任务、评审）；一个用户无法访问其他用户的会话（测试）。
  2. 事件和审计记录持久化到 PostgreSQL，事件通过 SSE 推送。
  3. 客户端断线重连时带上最后收到的事件编号，服务端补发缺失的事件（集成测试）。
  4. 确认请求能通过 API 完成。
  5. 服务层只依赖本项目的事件协议，不直接解析 pi 的原始事件。
  6. 接口写入 `contracts/session-api.md`。
- **是否需要评测**：否

## T5：每会话沙箱

- **目标**：服务中的每个会话在隔离环境中运行。
- **对应需求**：R4、R6
- **前置依赖**：T4
- **输入**：T2 的 Docker 执行器、T4 的服务
- **输出**：沙箱管理模块
- **验收标准**：
  1. 每个会话一个独立容器，整个 pi 进程（包括扩展）在容器内运行；会话结束后销毁容器。
  2. 容器有资源限制；网络只允许访问模型服务和代码托管平台，访问其他地址失败（测试）。
  3. 只注入当前会话专用、短期有效、限定范围的凭证，不注入长期密钥。
  4. 一个会话执行破坏性命令，不影响其他会话或宿主机（隔离测试，S4）。
- **是否需要评测**：否
- **所需环境**：Docker

## T10：并发与可靠性

- **目标**：多个会话同时运行时稳定可控，服务器崩溃后任务能继续。
- **对应需求**：R3
- **前置依赖**：T4
- **输入**：T4 的服务
- **输出**：API 与 worker 拆分、任务租约、Redis 限流与配额、压测报告
- **验收标准**：
  1. API 进程与 worker 进程分离；worker 领取任务时持有租约。
  2. 杀掉正在执行任务的 worker 后，任务从最近的检查点由其他 worker 继续；崩溃时正在执行的工具调用被标记为失败并告知模型，不自动重跑（故障注入测试，S5）。是否使用 pi-durable 开工前确定（proposal 第 6 节）。
  3. 用 Redis 实现模型调用限流与排队，以及按用户、按会话的 token 预算。
  4. 使用假模型压测 N 个并发会话，报告延迟与失败率。
- **是否需要评测**：否（压测报告写进 `docs/evals/`）

## T11：子 agent

- **目标**：用上下文隔离处理探索性工作（pi 不内置）。
- **对应需求**：R5、R6
- **前置依赖**：T3
- **输入**：T3 的薄桥与策略服务
- **输出**：子 agent 工具、子 agent 服务、一份决策记录

  1. 薄桥注册子 agent 工具；调用时由 Python 在同一沙箱内另起一个 pi 进程，只给只读工具和全新的上下文。

  4. 在探索型任务上对比"使用子 agent"与"只靠 pi 自带的上下文压缩"，产出评测报告。
