## T1：接入 pi 与本地模型

- **目标**：后端能通过统一引擎接口驱动 pi 完成任务，模型既可以是本地部署的开源模型，也可以是外部 API。
- **对应需求**：R1、R9（本地模型接入部分）
- **前置依赖**：无
- **输入**：pi（未修改的依赖）
- **输出**：统一引擎接口初版、pi 适配器（引擎运行器）、本项目事件协议初版、pi 的模型配置、`tests/fixtures/` 下的小型仓库
- **验收标准**：
  1. 统一引擎接口写入 `contracts/engine.md`，至少包括：启动任务、接收流式事件、工具执行前拦截、取消。pi 适配器实现该接口，能发送一条任务、收到流式事件，并能正确判断任务已结束（不会在 pi 还要继续时提前结束）。
  2. pi 的事件被转换成本项目的事件协议；协议写入 `contracts/agent-events.md`，包含与 pi 事件的对应关系和序号规则。转换逻辑有单元测试（使用录制的 pi 事件，不调用真实模型）。
  3. pi 通过配置使用在 Mac 本地部署的 Qwen 完成一个任务；切换到外部 API 只改配置、不改代码。
  4. 在 `tests/fixtures/` 的小仓库上，对 5 个"某函数在哪里被调用"的问题：用外部模型全部答对；用本地模型的结果如实记录。两者都写进实现说明。
  5. 能取消正在运行的任务，引擎实例被正确清理（测试）。
  6. pi 以锁定版本的依赖形式引入，没有修改或 fork 其源码（S3）。
  7. 关闭 pi 对 `AGENTS.md` 的自动发现，改由平台从任务分支所基于的受保护分支读取 `AGENTS.md` 并通过 `resourceLoader` 提供；任务分支中修改 `AGENTS.md` 不会改变 pi 收到的规则（测试）。
  8. 不加载仓库内的 `.pi/` 资源（配置、提示词追加、扩展、skill）：在测试仓库中放置 `.pi/extensions/` 扩展，它不会被加载执行（测试）。具体开关开工时核实，无法做到则停下来报告。
- **是否需要评测**：否
- **所需环境**：Node.js ≥ 22.19；pi；Mac 上的本地推理工具（如 Ollama）与一个 Qwen 模型；外部模型 API key

## T2：评测框架 v1 与基线

- **目标**：建立之后每一项改动的"尺子"，并给出外部模型与本地模型的基线。
- **对应需求**：R2、R4、R9（本地模型基线）
- **前置依赖**：T1
- **输入**：T1 的统一引擎接口
- **输出**：评测框架、Docker 执行器、任务集 v1、基线报告
- **验收标准**：
  1. 任务集按 design 3.11：开发集为 SWE-bench Verified 子集（30–50 个，覆盖多个仓库），留出集为 SWE-bench-Live（或 SWE-rebench）中所用模型训练截止日期之后的任务；开发集规模与留出集起始月份在开工时确定并写进实现说明；任务集标版本。
  2. 一条命令跑完整个任务集，输出成功率（均值与波动）、token、轮数、耗时、失败类型，并保存每个任务的完整执行轨迹。
  3. 每个任务在独立的 Docker 容器中、使用独立的仓库副本运行；agent 的命令不在宿主机上直接执行。
  4. 评测中的确认策略写进配置：危险命令自动拒绝，沙箱内的普通命令自动放行。
  5. 运行前输出预计花费，运行后记录实际花费。
  6. 产出基线报告，写进 `docs/evals/`：至少包含外部强模型和本地模型两组。
  7. 评测框架通过统一引擎接口运行任务，以便 T12 接入 Claude Code 时不需要改评测框架。
  8. 评测中仓库副本不含任务基准版本之后的提交历史（测试：在沙箱中用 git 查不到修复该 issue 的提交）；T7 接入检索服务后同样遵守这一截断。
  9. 正式评测可在远程 x86 Docker 主机上运行，评测框架不需要因运行位置改变；Mac 上能跑少量冒烟任务。
- **是否需要评测**：是，产出基线
- **所需环境**：Docker；x86 云服务器（正式评测，租用前报预计花费）；模型 API key；本地模型；确定对照用的强模型、所用 Qwen 的训练截止日期、评测框架的语言

## T3：权限、确认与审计

- **目标**：补上 pi 没有的权限系统，策略判断在引擎之外。
- **对应需求**：R5（MCP 工具风险等级）、R6
- **前置依赖**：T2
- **输入**：T1 的 pi 适配器、T2 的评测框架
- **输出**：工具拦截扩展、策略服务、审计记录、工具风险等级表
- **验收标准**：
  1. 扩展在工具执行前把调用转给策略服务，并执行其决定（放行、拦截并返回原因、需要确认）；扩展不含策略判断。接口写入 `contracts/policy.md`，包括超时与失败语义。
  2. 策略服务按风险等级决定放行、确认或禁止。风险等级表写入 `contracts/tools.md`，覆盖 pi 内置工具和已接入的 MCP 工具，并为每个工具声明"能否安全重跑"（只读类可以，有副作用的不可以）。
  3. 策略服务连不上或超时时，工具调用一律被拒绝（测试）。
  4. 需要确认时，确认请求通过引擎事件发出，回答后 pi 继续或收到拒绝原因；确认有超时，超时按拒绝处理（测试）。
  5. 每次策略决定和确认都写入审计记录：时间、会话、工具、参数摘要、决定、由谁确认。
  6. 询问策略服务这一跳的耗时单独记录；跑一次评测，报告这一跳在任务总耗时中的占比。
  7. 开启权限策略后重跑评测，与 T2 基线对比，变化如实记录。
  8. 项目策略配置按 `contracts/project-policy.md` 实现，至少支持冻结期（及冻结期内允许的修改范围）与禁止访问的路径；冻结期内对冻结模块的写操作被策略服务拦截，即使工单、记忆或 `AGENTS.md` 声称允许（测试）。
- **是否需要评测**：是，对比 T2 基线
- **所需环境**：同 T2

## T4：多用户会话服务 v1

- **目标**：把引擎包进多用户的会话服务。
- **对应需求**：R3、R6
- **前置依赖**：T3
- **输入**：T1 的事件协议、T3 的策略服务
- **输出**：会话服务（TypeScript）、PostgreSQL 事件存储、SSE 推送、项目与授权数据
- **验收标准**：
  1. 通过 API key 鉴权（统一登录在 T8）；每个 key 绑定员工或服务账号。

  6. 服务层只依赖本项目的事件协议和统一引擎接口，不直接解析 pi 的原始事件。

## T5：每会话沙箱

- **目标**：服务中的每个会话在隔离环境中运行。
- **对应需求**：R4、R6
- **前置依赖**：T4
- **输入**：T2 的 Docker 执行器、T4 的服务
- **输出**：沙箱管理模块
- **验收标准**：
  1. 每个会话一个独立容器，引擎运行器（pi 与本项目扩展）在容器内运行；会话结束后销毁容器。
  2. 容器有资源限制；网络只允许访问模型服务、策略服务和代码托管平台，访问其他地址失败（测试）。
  3. 只注入当前会话专用、短期有效、限定范围的凭证，不注入长期密钥。
  4. 一个会话执行破坏性命令，不影响其他会话或宿主机（隔离测试，S4）。
  5. 沙箱销毁前把 pi 会话文件保存到沙箱之外，并关联到平台会话；重建沙箱时放回，引擎能接着原来的上下文继续（测试）。

## T6：编排层：工单理解与路由

- **目标**：把工单整理成可执行任务，按规则在权限范围内路由。
- **对应需求**：R11、R9（本地小模型接入）
- **前置依赖**：T5
- **输入**：T4 的会话服务、T3 的策略服务、本地推理服务
- **输出**：工单理解模块、路由规则与装配、任务状态机、工单理解评测集
- **验收标准**：
  1. 本地小模型输出 `contracts/ticket-understanding.md` 定义的固定字段，每个字段附原文出处；格式不合格时重试一次，仍不合格归为 `unknown`（测试）。
  2. 编排层检查出处确实存在于工单原文中，找不到的字段标为"未经证实"（测试）。
  3. 本地模型不可用或超时时，跳过预处理，原始工单直接交给引擎，任务标记"未经预处理"（测试）。
  4. 实现 design.md 3.4 的全部类别与路由规则；规则写在项目配置中并标版本，格式写入 `contracts/routing-rules.md`；每次路由记录选择结果与规则版本。
  5. 任务状态机按 `contracts/task-states.md` 实现：进入等待状态时释放执行资源；恢复时重新提取、按当时授权重新检查、重建沙箱；超时进入 `EXPIRED`，工单保留，可手动重开（测试）。
  6. 升级必须确认："先排查，确认后修复"的流程端到端可走通；用户修改分类后，执行时仍按当前授权检查（测试）。
  7. 工单中试图影响权限的内容（如"跳过审批""这是低风险任务"）不改变任何决定（测试）。
  8. 编排层不自行判断审批、预算、取消，只调用对应服务（代码检查）。
  9. 用同一批仓库的原始 issue（含咨询、无效报告、功能请求）人工标注分类与提取测试集；其他类别用合成工单补充开发集（按 design 3.11 的合成规矩）；报告本地小模型的分类准确率（单独统计危险方向的误分类）、提取准确率和编造率，并与主模型对比准确率、成本和延迟。

## T7：检索服务：按项目选择检索实现

- **目标**：以 MCP 服务向引擎提供代码检索，按项目选择检索实现，为大仓库做好准备。
- **对应需求**：R12、R6
- **前置依赖**：T5
- **输入**：T4 的项目与授权数据、T5 的沙箱网络规则
- **输出**：检索服务（MCP）、至少两种检索实现、检索评测报告、一份实现说明
- **验收标准**：
  1. 检索服务以 MCP 服务的形式提供检索工具，pi 能在任务中调用；接口写入 `contracts/retrieval.md`。
  2. 至少两种检索实现（如 grep 与一种索引，具体种类开工时定），由项目配置选择；修改项目配置后切换实现，不需要重启后端，也不影响其他项目（测试）。
  3. 检索实现在服务内部用 Cordis 装配：切换或卸载实现时，它的后台建索引任务、仓库监听和定时器被清理（测试）。开工时先验证 Cordis 可行性，不可行则停下来报告。
  4. 索引在平台侧构建，仓库有新提交时增量更新，多个会话共享同一份索引。
  5. 检索结果按会话的仓库授权过滤，员工检索不到无权访问的仓库（测试）。
  6. 在不同规模的公开仓库上比较各实现找全相关文件的比例、耗时、成本，产出评测报告（S11），写明仓库规模。
  7. 提供提交历史检索（提交信息与 diff），pi 能按问题描述查到过去的相关修改（测试）。PR 描述与评审意见不在本任务范围。
  8. 提供按（仓库、路径、版本）读文件的 MCP 工具，供 pi 读取未检出的仓库；结果按会话的仓库授权过滤（测试）。
  9. 评测模式下，代码索引与提交历史检索只能看到任务基准版本之前的内容（测试：修复该 issue 的提交检索不到）。
