# 需求说明（proposal）

> 职责：做什么、不做什么、有哪些约束、怎样算成功。实现方案见 `design.md`，工作项见 `tasks.md`。

## 1. 背景

作者正在投递国内互联网大厂的 AI Agent 开发、大模型应用开发岗位，简历投出后没有回音，无法判断是项目深度不够还是 HC 不足。本项目的目的是做一个经得起面试深挖的项目，至少排除"项目深度不够"这一因素。作者要投寒假实习，**2026 年 11 月底**需要有一个能写进简历的版本。

### 产品定位

**面向企业内部部署的 coding agent 平台。** 各方面能力按企业级的要求来设计，但项目没有企业数据，一律用公开数据模拟。由此得出一条设计前提：**代码和数据不出部署方**，系统必须能使用部署在本地的模型完成任务，外部模型 API 只是可选项。

产品通过一个工作台提供三种模式，三种模式共享同一套后端能力，不是彼此独立的系统：

- **对话模式**：解决开发者不熟悉项目、查找代码和理解逻辑耗时的问题。通过代码问答帮助理解项目、定位问题。
- **任务模式**：解决 Bug 修复、功能开发中理解工单、定位、修改、测试的重复劳动。输入工单，执行处理，交付可审核的 PR。
- **评审模式**：解决 AI 生成代码快、人工 Review 跟不上的问题。把修改后的 PR 按逻辑组织成清晰、可视化的变更说明，帮助人理解修改目标、实现思路和影响范围。

### 术语

- **Harness / Agent 引擎**：agent loop、内置工具、上下文压缩等运行时。默认使用 pi，不自研。
- **编排层**：本项目编写的流程控制与运行管理代码，位于 Agent 引擎之上，负责把用户需求整理成可执行任务、按规则路由，并串联权限、审批、会话等服务。

### Agent 引擎复用 pi

Agent 引擎直接使用 pi（<https://github.com/earendil-works/pi>，MIT 许可），不自研。理由：作者简历上已有 Agent Harness 的经验（私募客服 Agent 的 Harness 重构），再自研一遍是重复，并且会占掉 11 月底前的大部分时间。决策见 `decisions/001-reuse-pi-as-harness.md`。

**取舍规则：pi 自带的能力不重做；pi 不带的，由本项目实现。** 只省略自研 Harness 这一部分，其余范围全部保留。

编排层通过统一的引擎接口驱动 Agent 引擎。pi 是产品的默认引擎；Claude Code 只作为评测中的对照引擎，不进入产品（见 `decisions/005-engine-interface-and-2x2-eval.md`）。

### 项目目的

1. **求职信号**：覆盖目标 JD 中反复出现的要求：Skill / Tool 体系、评测、沙箱与安全隔离、身份与权限、后端高可用与容器化，以及作为加分项的模型本地部署与微调。
2. **真正学会**：作者要真正学会后端、模型部署与微调，而不是只做到能演示。前端不在此列（见 3.2）。

### 与作者已有项目的关系

作者已有一个私募客服 Agent 项目，覆盖：主管 Agent（ReAct）与子 Agent 的意图分工、分层记忆、业务工具调用容错、合规护栏、对话评测，以及 Harness 重构。

本项目与之**互补而不是重复**，侧重：

- 复用成熟 Harness，把重点放在 Harness 之上的企业能力（不是再写一遍 Harness）
- 工单理解与规则路由（不是对话意图分工）
- 上下文隔离的子 agent
- 高风险工具（文件编辑、bash）的权限、审批与沙箱
- 可客观判定的评测（测试是否通过）
- 后端服务工程、模型本地部署与微调

## 2. 目标

| 编号 | 需求 |
|---|---|
| R1 | **Agent 引擎集成**：编排层通过统一引擎接口驱动 Agent 引擎。pi 为默认引擎，其自带的 agent loop、内置工具、失败重试、上下文压缩、skill 加载、MCP 客户端直接使用，不重写。Claude Code 作为评测对照引擎接入同一接口，不进入产品 |
| R2 | **评测体系**：尽早建立，之后每一项声称"更好"的改动都用评测数据说明（eval-first） |
| R3 | **多用户、多会话服务**：员工通过统一账号登录（SSO），程序通过绑定到员工或服务账号的 API key 访问；会话持久化；流式推送；断线重连后补发事件；服务器崩溃或重启后正在执行的任务能继续；并发、限流与按用户配额 |
| R4 | **沙箱隔离**：agent 执行的命令运行在隔离环境中，一个会话的破坏性操作不影响其他会话或宿主机 |
| R5 | **Agent 引擎之上的扩展能力**：子 agent（pi 不内置）；skill 按团队、按用户分发，带权限、版本与审计，并能评测 skill 的效果（加载机制用 pi 自带的）；MCP 工具纳入风险等级与权限管理（MCP 客户端用 pi 自带的） |
| R6 | **身份与权限**：员工身份 → 团队 → 项目 → 可访问的仓库与允许的操作，形成一条授权链，并传递到 Agent、子 agent、skill 与 MCP 插件；权限从工具级、agent 级、会话级到沙箱级逐层收窄；高风险操作经人确认或审批；平台内置审批流程（如仓库权限申请），审批通过后自动授权；agent 永远不能审批或授权；每次确认、审批与工具调用都可追溯 |
| R7 | **可观测**：任意一个失败的任务都能定位到出错的那一步 |
| R8 | **可复现**：他人 clone 后能跑通；README、架构图、评测报告齐全 |
| R9 | **本地模型部署与微调**：系统能使用部署在本地的开源模型完成任务，代码和数据不出部署方。首个微调对象是编排层的工单理解小模型（信息提取与分类），用公开数据训练，并用评测说明效果。用执行轨迹微调整个 agent 以后再定 |
| R10 | **企业工作台**：网页工作台提供对话、任务、评审三种模式，共享后端能力；用户在这里提问、下发任务、补充要求、确认方案、查看进度、审核结果。每种模式背后都必须有真实的后端能力，并由评测或演示证明 |
| R11 | **编排层：任务理解与路由**：本地小模型理解工单（提取现象、触发条件、实际结果、预期结果、缺失信息，给出分类建议）；编排层校验模型输出、组装执行上下文、按规则在权限范围内路由；需要用户补充信息或确认时，任务进入可恢复的等待状态；分类结果不能代替权限判断 |

## 3. 范围

### 3.1 包含

R1 至 R11 的全部内容。具体工作项见 `tasks.md`。

- K8s 是**有条件的**：每会话 Docker 沙箱必做；K8s 只用于演示多节点调度与资源配额，时间紧张时可以砍掉。
- 任务拆分与顺序见 `tasks.md`：11 月底前完成 T1–T5（接入 pi 与本地模型、评测与基线、权限确认与审计、多用户会话服务、每会话沙箱），即里程碑 v0.5。

### 3.2 非目标

- 不自研 Agent Harness：agent loop、内置工具、上下文压缩、skill 加载、MCP 客户端都用 pi 自带的
- Claude Code 不进入产品，只在公开数据的评测中作为对照引擎
- 不做角色扮演式的多 Agent（规划 Agent + 编码 Agent + 测试 Agent 之类）
- 前端以展示产品完整性为目的，不追求前端技术深度；前端主要由 AI 辅助完成，作者只需讲清每个模式调用的接口、数据流和流式显示方式
- 不从零预训练模型
- 不使用任何企业内部数据，需要企业数据的场景一律用公开数据模拟
- 不对接外部的工单、审批、运维系统；需要转交的请求在平台内生成记录
- 不追求在功能上覆盖 Claude Code、Cursor 等产品

### 3.3 反目标

以下情况即使技术上能跑通，也算失败：

- 说不清哪些能力是 pi 提供的、哪些是本项目做的；或把 pi 的能力说成自己做的。
- 只有功能、没有数据。任何声称"更好"的改动都必须有评测对比，否则不写进简历。
- 为了凑 JD 关键词而引入组件。每个组件都必须对应一个真实问题。
- 编造或夸大指标。评测结果如实记录，包括负面结果。
- 把用公开数据模拟得到的结果说成企业真实数据上的结果；或引用不是本项目测出的指标（例如外部材料里的提升比例）。
- 本地部署与微调只为凑关键词：它们必须对应"数据不出部署方"这一前提，并有评测数据说明效果。
- 工作台只有界面、背后没有真实能力。
- 为了实现功能去修改 pi 的源码，导致无法跟随 pi 升级。
- 模型的分类、工单内容或 agent 的输出能够绕过权限判断，或 agent 能够审批、授权。
- 用户等得久或忘了回复，被当作继续执行的依据。

## 4. 成功标准

| 编号 | 标准 | 测量方式 | 目标值 |
|---|---|---|---|
| S1 | agent 在留出集上的任务成功率 | 评测框架，多次重复取均值与波动 | 待定（建立基线后确定） |
| S2 | 每项声称"更好"的改动都有评测对比 | 检查 `evals/` 中有对应报告 | 全部满足 |
| S3 | pi 以未修改的依赖形式使用，本项目的能力都通过 SDK、RPC 与扩展接入 | 检查依赖与代码：没有 pi 源码的修改或 fork | 无修改 |
| S4 | 一个会话执行破坏性命令，不影响其他会话或宿主机 | 隔离测试 | 通过 |
| S5 | 服务器崩溃或重启后，正在执行的任务能继续 | 故障注入测试 | 通过 |
| S6 | 任意失败任务都能定位到出错的那一步 | 抽查失败任务 | 全部可定位 |
| S7 | 他人按 README 能跑通 | 在干净环境中验证 | 通过 |
| S8 | 本地模型与微调效果有评测对比 | 工单理解：小模型原版、微调后、主模型三方对比准确率、成本、延迟；端到端：外部强模型与本地模型对比 | 待定（建立基线后确定） |
| S9 | 工作台三种模式都能端到端跑通，且背后的能力有评测或演示证明 | 每种模式一个端到端演示；任务模式的成功率来自评测 | 通过 |
| S10 | 编排层的价值有评测证明 | 2×2 对比（pi / Claude Code × 有无编排层）；分类准确率（单独统计危险方向的误分类）；提取准确率与编造率 | 待定（建立基线后确定） |

## 5. 约束

- **人力**：作者一人，每周 7 天，每天 5–6 小时，合计约 35–40 小时。
- **硬件**：一台 macOS 电脑。K8s 如果做，使用 kind 或 k3d 本地集群。微调和推理服务部署在 Mac 上跑不动时，可以租 GPU。
- **成本**：模型调用走 API，微调与部署可能租用 GPU。**暂不设预算上限**，出现明显超支时再讨论。每次跑评测或租用 GPU 前，先报告预计花费；跑完后在评测报告中记录实际花费。
- **时间**：
  - **2026 年 11 月底**：完成 T1–T5（里程碑 v0.5），写进简历、投递寒假实习。
  - 之后按 `tasks.md` 的依赖推进，不预设每个任务的完成日期。
- **语言**：后端（编排层、引擎适配器、会话服务、策略服务、审批、沙箱管理）与工作台前端都用 TypeScript；微调用 Python；评测大概率用 Python。决策见 `decisions/003-typescript-as-main-language.md`。
- **模型**：开发使用 Qwen；本地部署使用开源权重模型，型号待定；工单理解使用本地小模型；对照用的强模型待定。
- **作者背景**：前后端基础偏弱，熟悉 Agent 概念与评测，已有 Agent Harness 经验。
