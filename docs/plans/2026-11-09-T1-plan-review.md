## 一、计划要改（按严重程度）

1. **高：缺少调用方从本地 git 基准引用读取 `AGENTS.md` 的完整链路。**（计划 Task 7；T1 验收 7、10；ADR 008）
   Task 7 只验证手工传入的 contextFiles 被注入。即使调用方错误地读取任务分支工作树，这些测试仍可能通过，没有覆盖验收 10 要求的"调用方从本地 git 引用读取"。
   建议：增加调用方侧读取的小任务，明确仓库、基准引用、文件路径的输入及缺失处理；测试先从指定基准引用取规则，再修改任务分支中的文件，证明运行器仍收到基准版本。运行器继续只接收内容，不负责读取 git。

2. **高：计划自行允许绕过开工环境关卡。**（计划环境表；workflow 3.7.4）
   计划报告缺少 Ollama 和 API key，却直接规定 Task 1–8 可以先做；工作流要求环境不可用时报告、由作者决定。Task 0 又规定"任何一项不成立就停下来"，前后不一致。
   建议：区分"小模型任务做不对不阻塞"和"本地推理环境没有准备好"，后者不能豁免实际运行。（作者已决定：环境已补齐，不分阶段。）

3. **高：确认流程的依赖顺序和接口对不上。**（计划 Task 6、Task 8 客户端接口；T1 验收 1）
   Task 6 指定确认由 runner 处理，却要求在 Task 8 创建 runner 之前通过确认往返测试；其输入只有返回 allow/block 的 EngineHooks，没有独立的确认协调接口。协议要求 `confirm_response.by`，客户端接口没有身份来源；客户端的拦截回调也无法返回协议支持的拒绝原因。
   建议：先拆出可独立测试的拦截与确认协调模块，再接扩展，最后接 WebSocket；或将确认往返测试移到 Task 8。补齐确认人、拒绝原因、确认超时和迟到答复的约定。

4. **高：终止、取消和错误语义不足以形成唯一的行为约定。**（计划 Task 2、5、8；T1 验收 1、5）
   转换器产生 `run.settled`，引擎另外产生失败、取消事件，但未明确谁保证三者互斥、只发一次，以及如何统一分配序号。取消测试只有慢文本流，没有覆盖等待拦截决定、等待确认或工具执行中。`waitForEnd()` 未规定收到 `not_implemented`、连接断开时如何结束；测试要求"runner 上报 disposed"，协议却没有对应字段。
   建议：补充状态与结束规则、事件序号的唯一分配方、取消时清理等待请求的方式、客户端错误传播方式；明确任务结束后是否接受下一次启动、断线后进程何时退出，并为清理提供明确的测试观察方式。

5. **高：资源隔离的验证范围小于规范要求。**（计划 Task 0 Step 1、Task 7；design 3.15.3；ADR 008）
   测试验证了扩展和 `APPEND_SYSTEM.md`，但 `.pi/settings.json` 只有文件、没有行为断言；skill 只有 `.agents/skills` 样本、没有相应断言，也没有 `.pi/skills` 样本。发现范围包含上级目录，"临时目录为空"本身不足以证明自动发现已关闭。
   建议：开工核实明确包含上级目录、用户目录及配置引用的资源路径；为配置和 skill 增加可观察的负向验证。将"只加载平台注入资源"作为必须证明的行为，具体 SDK 做法以核实结果为准。

6. **中：模型核实缺项，本地型号没有实际产出步骤。**（计划 Task 0 Step 4、Task 9 Step 4；T1 验收 3；ADR 015）
   Task 0 没有安排"通过 pi 调用时工具调用正常"的真实探测；Task 9 引用"Task 0 确定的小模型"，但 Task 0 只写了两个主模型候选。公开资料、价格、许可证查询不必等待 key。
   建议：拆开公开资料核实与凭证探测；明确产出本次 API 候选、平台、固定版本，以及本地小模型的型号、量化、版本或摘要；用最小 pi SDK 探测证明工具调用往返正常并记录证据。另一候选的完整接通比较仍留给 T2。

7. **中：执行环境清单不完整，脚手架步骤无法按预期顺序运行。**（计划环境表、Task 1、Task 10；workflow 2.5、3.7.4）
   没有工作区脚手架时，Task 1 却要求先运行 vitest 并预期因函数不存在而失败。协议包使用 zod，但依赖只安排给 runner。计划创建了 build 脚本，收尾却不运行构建或类型检查。
   建议：先建立最小测试环境，再进行红绿测试；明确包间依赖、各包依赖和构建入口。环境检查补充 Git、bash、依赖下载与文档访问、测试所需本地端口及子进程能力、所引用的执行技能是否可用；Ollama 检查服务与实际模型，API 检查凭证注入及可调用性。

8. **中：真实录制与五题判定的证据链不完整。**（计划 Task 2 Step 1、Task 9；T1 验收 2、4；design 原则 5）
   手写样本不能作为"录制事件"的证据；EngineClient 只接收转换后的事件，脚本却承诺保存原始 pi 事件，没有采集通道。五题未规定回答格式、漏报/多报如何判分；检查标准答案所在行有调用，只能证明列出的答案存在，不能证明完整或排除同名干扰。脚本声称只读，却对所有工具一律放行。
   建议：先用假模型驱动真实 pi 录制基础样本，真实模型录制再补充；原始事件由 runner 的诊断设施采集。明确逐题判分规则、答案完整性检查、五题是否独立会话，并在调用方落实只读工具范围。

9. **中：部分小任务明显偏大。**（计划 Task 0、8、9；workflow 2.5）
   建议按独立可验证的产出拆分：开工能力核实／模型核实；runner／客户端／跨进程异常验证；题库与判分／API 运行／本地运行与录制。给每项标预计耗时和显式依赖，安装下载等待单独记录。

10. **中：收尾顺序与工作流不一致。**（计划 Task 10；workflow 3.4）
    建议按工作流排列：整体审查并处理问题 → 最终验收核对 → 实现说明及账本转存 → 一致性检查 → 作者不看代码回答自测题 → 作者明确同意。收尾材料可提前准备，但需在审查后确认有效。

11. **低：局部写法过细，但关键行为仍留白。**（计划 Task 1 测试代码、Task 4 假服务、Task 0 文档行号引用；workflow 2.4–2.5）
    建议保留接口、行为、输入输出和验证命令，删除不影响行为的编码细节（完整测试函数体、临时文件写法、指定 HTTP 实现等）。假服务脚本耗尽应明确报错，而不是重复最后一个文本回合。外部文档引用使用固定版本和章节/符号，不写"第 116 行"；Spec 补上 design 8.1 与工作流入口。
