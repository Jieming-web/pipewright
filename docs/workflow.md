# 开发工作流

本文件是项目开发工作流的**唯一权威来源**。`CLAUDE.md` 中的规则只是本文件的摘要，两者冲突时以本文件为准，并应修正 `CLAUDE.md`。

使用方式：不必每次通读全文。按当前所处环节读取对应章节：

| 当前环节 | 读哪一节 |
|---|---|
| 新建或修改规范文档 | 第 2 节 |
| 开始执行一个任务 | 第 3 节 |
| 需求、方案、任务发生变化，或发现结果不符合预期 | 第 4 节 |
| 写启动执行的提示词 | 附录 A |

---

## 1. 概念与价值

本工作流同时服务两类读者：

- **作者**：要真正学会、能在面试中讲清每一个设计。
- **AI**：按约定执行，不自由发挥。

它要守住六件事：

| 价值 | 机制 |
|---|---|
| 减少歧义 | 实现前写清范围、约束和成功标准，避免一句需求有多种理解，在实现前暴露分歧 |
| 保留约定 | 规范保存为可重新读取的项目文件，而不是只存在于聊天中，让新会话或接手者能延续已确认的要求 |
| 结果可验证 | 先定义测试与验收标准，强制 AI 实际运行测试；没有验证证据不算完成 |
| 代码可追踪 | 每个步骤交付实现说明：做了什么、设计意图、代码在哪、与计划的偏差，使人无需逐行 Review 也能快速理解 |
| 真正学会 | 不区分代码由谁编写；每个步骤结束时必须通过严格的讲解自测 |
| 证据可信 | 评测数据与代码版本、模型、任务集版本一一对应，负面结果同样记录 |

## 2. 规范结构

### 2.1 目录

```
coding-agent/
├── CLAUDE.md                    # 规范索引 + 硬规则摘要
├── docs/
│   ├── workflow.md              # 本文件：开发工作流
│   ├── templates/               # 各类文档的模版
│   ├── specs/                   # 规定"应该是什么"（权威来源）
│   │   ├── proposal.md          # 背景、目标、范围与非目标、成功标准、约束
│   │   ├── design.md            # 架构、模块职责、关键流程、数据模型、非功能设计
│   │   ├── tasks.md             # 工作项、输入输出、依赖、验收标准、完成状态
│   │   ├── contracts/           # 按需拆出的接口与数据约定
│   │   └── decisions/           # 按需拆出的架构决策记录（ADR）
│   ├── plans/                   # 单个任务的执行计划（writing-plans 产出）
│   ├── reviews/                 # 实现说明
│   └── evals/                   # 评测报告
├── src/
└── tests/
```

`specs/` 存放规范，即"应该是什么"。`plans/`、`reviews/`、`evals/` 记录"打算怎么做"和"实际发生了什么"，不属于规范，因此放在 `specs/` 之外。

### 2.2 各文档的职责

| 文档 | 职责 | 不应包含 |
|---|---|---|
| `specs/proposal.md` | 项目背景、目标、需求范围与非目标、成功标准、约束条件 | 实现方案 |
| `specs/design.md` | 系统架构、模块职责、关键流程、数据模型、非功能设计 | 工作项与进度 |
| `specs/contracts/*.md` | 模块间接口、输入输出结构、行为约定、错误与状态语义 | 内部实现细节 |
| `specs/decisions/NNN-*.md` | 重要架构取舍的背景、备选方案、决策、理由、状态，以及"pi 的做法" | 与取舍无关的说明 |
| `specs/tasks.md` | 步骤级工作项：目标、输入输出、前置依赖、验收标准、完成状态 | 1 小时粒度的执行细节 |
| `plans/日期-主题.md` | 把 tasks.md 的一个任务拆成约 1 小时一个的小任务：文件、接口、测试、验证命令 | 重复抄写验收标准（只引用） |
| `reviews/stepNN-主题.md` | 做了什么、设计意图、代码地图、与计划的偏差、验证记录、已知限制、讲解自测题 | 规范性要求 |
| `evals/日期-stepNN.md` | 代码版本、模型、任务集版本、重复次数、结果、失败分类、花费、结论 | 修改过的历史结论 |

各类文档的模版见 `docs/templates/`。

### 2.3 组织原则

1. **按职责组织内容。** 需求说明做什么、不做什么、有哪些约束、怎样算成功；设计说明如何实现；任务说明具体工作、依赖和验收标准。不同职责的内容不混在同一个文档。
2. **围绕任务提供必要上下文。** AI 执行任务时能获得全局上下文（目标、架构与核心约束）、任务上下文（当前任务的描述、输入输出与验收标准）和前置上下文（依赖的已有代码与模块）。
3. **提供清晰的入口和引用。** `CLAUDE.md` 提供规范索引与必要摘要；执行任务时引用相关规范章节和已有代码位置。
4. **单一权威来源。** 每个约定只在一处定义，其他文档通过引用或必要摘要使用，避免多处独立维护导致内容矛盾。例如验收标准只写在 `tasks.md`，`plans/`、`reviews/` 只引用。

### 2.4 写到什么程度

以"恰好够 AI 执行"为准：关键要求不留给 AI 猜测，局部编码细节不必提前规定。

- **需求层面的要求必须明确**：功能范围、输出结果、性能指标、异常处理边界等，写在 `proposal.md`。
- **架构层面的选择在设计中明确**：模块分工、接口、数据模型和重要方案，写在 `design.md`、`contracts/` 或 `decisions/`。
- **只影响代码写法、不改变最终行为的细节交给 AI**：但仍须遵守项目已有的编码规范。

- **写得不够的信号**：AI 经常猜错关键行为，需要在对话中反复纠正。这些纠正涉及的要求应补回对应规范（见 4.5）。
- **写得过细的信号**：连不影响最终行为的局部写法也逐项规定，文档变成代码的逐行说明，维护成本超过收益。

### 2.5 tasks.md 与 plans/ 的分工

- `tasks.md` 只写到步骤级（当前为 T1–T15，以及后续新增的任务）。这一层相对稳定。
- 每开始一个任务时，才用 writing-plans 把它拆成约 1 小时一个的小任务，写进 `plans/`。后续步骤会被前面的实际结果改变，提前细拆大多会白写。
- 小任务格式：目标、修改文件、实现类与函数签名、验收方式、测试命令。
- 外部依赖（模型 API、网络、容器）在单元测试中一律使用 Fake 或 Mock。
- 进度标记：`[ ]` 未开始、`[~]` 进行中、`[x]` 已完成，附完成日期和一行备注。

## 3. 执行流程

### 3.1 流程总览

```
1. 选择前置依赖已满足的任务
   └ 从 tasks.md 选一个依赖项都已是 [x] 的任务
   └ 用 writing-plans 把它拆成约 1 小时一个的小任务，写进 plans/，作者审过后开工
   └ 在计划里按顺序取下一个小任务
        ↓
2. 获取三类上下文（每一类都有固定来源）
   ├ 全局：CLAUDE.md → proposal.md、design.md 的相关章节 → 计划头部的全局约束
   ├ 任务：计划里这个小任务的说明 + tasks.md 里这一任务的验收标准
   └ 前置：小任务说明中的 Interfaces 一栏 + 所依赖代码的文件位置 + 相关 contracts/
        ↓
3. 依据上下文实现代码与测试（先写测试、看它失败，再写实现）
        ↓
4. 实际运行测试，对照验收标准（必须当场运行、读过输出）
        ↓
5. 验收通过？
   ├ 否，是代码 bug → 修复 → 重新验证 → 回到 4
   ├ 否，是计划或规范的问题 → 停下来问作者 → 作者拍板后记录 → 回到 3
   └ 是 → 记录验证结果、本地提交 → 6
        ↓
6. 还有任务？
   ├ 计划里还有小任务 → 回到 1 取下一个
   └ 这一任务的小任务全部做完 → 任务收尾关卡（见 3.4）：
        a. 整体代码审查
        b. 对照 tasks.md 的验收标准逐条核对
        c. 改变了 agent 行为的话，跑评测，写进 evals/
        d. 写实现说明 reviews/stepNN.md
        e. 严格的讲解自测
        f. 作者明确同意
      → tasks.md 标 [x]、经作者同意合并回 main → 回到 1 选下一个任务
   └ 所有任务都完成 → 结束
```

### 3.2 六个环节

#### 1. 选择当前要执行的任务

先从 `specs/tasks.md` 中选择一个尚未完成、前置依赖已经满足的任务，明确这一次要交付什么。第一次执行时，从没有前置依赖的任务开始；已有部分成果时，根据当前进度选择可以继续推进的任务。

先确定任务，再围绕这个任务获取上下文，而不是先把所有文档都塞给 AI，再让它随意决定做什么。

开工前用 writing-plans 把任务拆成小任务写进 `plans/`，作者审过后开工。计划头部的 Spec 字段同时指向 `proposal.md`、`design.md`、`tasks.md` 中的对应条目，以及相关的 `contracts/`。

#### 2. 根据任务获取三类上下文

确定当前任务后，获取与它相关的三类信息。每个任务都重新获取，不沿用上一个任务的上下文。

| 上下文 | 包含什么 | 从哪里获取 |
|---|---|---|
| 全局上下文 | 项目目标、架构与当前任务涉及的约束 | 通过 `CLAUDE.md` 的索引，读取 `specs/proposal.md`、`specs/design.md` 及相关契约章节；计划头部的全局约束 |
| 任务上下文 | 当前任务的描述、输入输出和验收标准 | `specs/tasks.md` 中的当前任务条目；`plans/` 中对应小任务的说明 |
| 前置上下文 | 当前任务依赖的已有代码与模块，避免重复实现或接口不一致 | 前置任务产出的代码、测试及现有共享模块；小任务说明中的 Interfaces 一栏 |

#### 3. 实现代码与测试

依据当前任务及相关规范实现代码，同时编写对应的测试。实现遵守设计中的模块边界和接口约定，测试对照任务的验收标准，检查应交付的行为。

- 先写测试并看到它失败，再写实现（superpowers:test-driven-development）。
- 测试分工见 3.5。

这一阶段的产出是代码和测试，还不能据此认定任务已经完成。

#### 4. 运行验证，未通过则修复

实际运行测试，逐项对照 `specs/tasks.md` 中当前任务的验收标准检查结果；涉及需求或接口行为时，同时核对 `specs/proposal.md` 和相应的契约定义。必须当场运行并读过输出（superpowers:verification-before-completion）。

- **未通过**：根据失败结果修复当前任务，再次运行验证。同一个任务最多返修 **3 轮**。遇到规范冲突、环境阻塞或达到返修上限时，暂停并报告，而不是无限重试（见 3.3）。
- **通过**：进入记录结果、标记完成这一步。

"代码生成完了"不是完成条件，"验收通过了"才是。未执行的检查必须注明，不能当作已经通过。

#### 5. 记录结果，标记任务完成

验收通过后，记录实际执行的检查及其结果，再更新完成状态。不要默认 AI 会自动写回进度，责任划分如下：

- **小任务（plans/）**：AI 在验证通过后勾选，并记录实际执行的命令和结果。
- **任务（tasks.md）**：所有小任务完成后，先通过任务收尾关卡（3.4）。AI 负责写入状态、完成日期、一行备注和验证记录，**只有作者同意后才能标 `[x]`**。

#### 6. 选择下一任务，继续循环

检查 `specs/tasks.md` 中是否还有未完成的任务：有，则回到第 1 步，选择前置依赖已满足的下一项，并重新获取与它相关的上下文；没有，则结束本轮执行。如果仍有未完成任务，却没有可执行项，应报告依赖或阻塞问题，不继续空转。

### 3.3 遇到问题停下来问作者

本项目覆盖 superpowers 执行类技能"执行中不停顿、由 AI 自行裁决"的默认规则。

**必须停下来问作者：**

- 规范或计划没写清楚，而不同做法会改变 agent 的行为
- 计划与规范矛盾，或前后任务的接口对不上
- 想偏离计划：多做、少做或换一种做法
- 测试或评测结果不符合预期，而原因可能是计划或规范本身有误
- 同一任务返修达到 3 轮上限，或遇到环境阻塞（缺依赖、API 不可用等）
- 不可逆或破坏性的操作、涉及安全的操作、影响工作区之外的操作
- 拿不准问题属于"实现有误"还是"规范遗漏"时（见 4.2 路径 1），一律按"规范遗漏"处理并停下来

**不用问，AI 可以自行决定：**

- 只影响写法、不影响行为的细节：变量命名、辅助函数拆分、循环写法等，但须遵守项目编码规范
- 规范正确、只是实现有误的代码 bug：按 superpowers:systematic-debugging 找到根因，先写能复现问题的测试，再修复；修复后在实现说明中记录

**怎么问：**

说清卡在哪里、有哪几种做法、各自的影响，并给出建议。作者拍板后，把决定记进当前任务的实现说明；属于重要架构取舍的，另写一份决策记录。

### 3.4 任务收尾关卡

tasks.md 中的一个任务要标 `[x]`，必须依次通过：

1. 所有小任务完成、全部测试通过，并做一次整体代码审查（superpowers:requesting-code-review）
2. 对照 `tasks.md` 的验收标准逐条核对，不能只凭"测试通过"
3. 如果改变了 agent 的行为，跑评测，写进 `evals/`
4. 写好实现说明 `reviews/stepNN-主题.md`，包含"验证记录"和"与计划的偏差"两节。superpowers 执行账本中的裁决和修过的 bug，在账本删除前转存到这里
5. 收尾一致性检查（见 4.6）
6. **严格的讲解自测**：AI 按实现说明中的讲解自测题提问，作者不看代码作答。答不上来，这一任务就不算完成，弄懂后再继续
7. 作者明确同意

### 3.5 测试分工

- **确定性逻辑**（工具执行、上下文裁剪、事件协议等）用单元测试，模型一律使用 Fake。
- **agent 整体表现**用评测，看统计结果。
- 两者不能互相替代。

### 3.6 提交与发布权限

- AI 可以在任务分支上做**本地提交**，每个小任务一次。
- **推送、合并回 main、打 tag、发布**必须经作者同意。

### 3.7 如何用 AI 推进

#### 3.7.1 提示词：明确这一次怎样推进

提示词是启动执行的触发器。除了"按照规范实现"，还应明确：

- 本次只做一个任务，还是按依赖连续做几个
- 通过哪些文件和章节获取上下文
- 完成后怎样验收
- 由 AI 还是作者更新进度
- 遇到什么情况需要停下来

如果希望连续推进，就把范围改为指定的任务集合，并要求"前一任务验收通过后，再选择依赖满足的下一项"。不同模型对指令的响应、不同 Harness 对上下文加载、权限和任务状态的处理并不相同，因此提示词需要结合实际框架和任务适配，不能复制后就默认所有行为都会发生。

模版见附录 A。

#### 3.7.2 Agent 编排：决定谁来做、怎样交接

- 简单任务用一个 Agent：由它读取规范、实现和验证。
- 任务较多、存在独立工作，或需要独立审查时，再考虑多个 Agent：主 Agent 负责派发和汇总，子 Agent 负责限定范围的实现或审查。
- 派发时给出任务编号、规范引用、前置产物、修改边界和验收要求，不能假定子 Agent 已经知道主会话的全部背景。
- 独立任务由子 Agent 向主 Agent 返回改动、测试证据和阻塞即可，不必让所有 Agent 互相通信。确实需要协商接口时，先确认框架支持相应通信，并约定谁确认变更、谁更新进度。通信机制不能代替统一的接口契约。
- 并行不是默认选择。只有前置依赖已满足、修改范围和共享资源不冲突的任务才适合并行，最后仍需统一做集成验证。
- 在 Claude Code 中：
  - 默认使用子 Agent（superpowers:subagent-driven-development 或 superpowers:executing-plans）。
  - 多 Agent 编排（Workflow 等）消耗大量 token，只有作者明确要求时才启用。
  - **子 Agent 做完一个任务即销毁**，避免上下文腐烂。
  - **上下文只用约 50%**：小任务拆得足够小，让子 Agent 用不到一半的上下文就能完成；主会话用到一半左右时，通过 `tasks.md`、`plans/` 和执行账本交接给新会话，不等自动压缩。

#### 3.7.3 推进模式：决定按什么节奏执行

- **规划与执行**：先形成或核对计划，再按步骤执行。`proposal.md` 提供目标，`design.md` 提供约束，`tasks.md` 承载计划。AI 可以辅助规划，作者确认后再执行；已有明确计划时不必重新拆解；发现计划或规范有问题时反馈调整，而不是边写边擅改目标。
- **生成与评审**：实现后按规范检查，发现不符合项就返修，通过后再继续。可以由同一个 Agent 分阶段完成，也可以交给独立的审查 Agent；两种方式都需要实际的验证证据，并设置返修上限。
- **护栏三明治**：执行前检查范围、权限和必要输入，执行后检查产出与验收结果。适合机械检查的规则，通过 Harness 的权限机制、Hooks 或测试脚本来落实，而不只靠提示词提醒（建议配置见附录 B）。

这些模式可以组合使用。例如"核对计划 → 执行当前任务 → 测试与评审 → 记录结果 → 下一任务"就是一个轻量的推进安排。不需要为了使用模式而额外搭建一套框架。

#### 3.7.4 工具与 Skill：提前准备执行和验收能力

验收方法写进文档，不等于 AI 已经具备对应的能力。每个任务开工前，在计划中列出它需要的执行与验收环境（例如 Docker、kind 集群、模型 API key、评测用的测试仓库），并**先检查是否可用**。不可用时停下来报告，由作者决定是补齐能力还是修改方案。

## 4. 变更与版本维护

### 4.1 原则

**找到受影响的最上游层级，从那里开始修改，再向下检查影响。** 先判断问题出在哪一层，而不是一遇到变化就直接改代码，也不是每次都把全部规范重写一遍。

```
需求（proposal.md）
     ↓
设计（design.md、契约 / ADR）
     ↓
任务（tasks.md）
     ↓
实现（代码）
     ↓
验证（测试与验收）
```

箭头表示需要检查的依赖关系，不是每一层都必须修改。契约和 ADR 属于设计相关材料，不单独成为阶段。

| 变更类型 | 修改起点 | 对应材料 |
|---|---|---|
| 需求变化 | 需求 | `proposal.md` |
| 方案变化 | 设计 | `design.md`、契约 / ADR |
| 任务调整 | 任务 | `tasks.md` |
| 普通实现 bug | 实现 | 代码 |

需求变了，要向下检查设计、任务、实现和测试；如果只是代码没有遵守正确的规范，就从实现层修复，不必倒过来修改需求来迁就错误代码。

**谁来判断**：AI 先复现问题，判断属于下面哪条路径，把判断结果和受影响范围报告给作者，作者确认后再修改。唯一例外是路径 1 情况 A（规范正确、实现有误），按 3.3 由 AI 直接修复。

### 4.2 四条处理路径

**路径 1：结果不符合预期**

先复现，再对照规范判断偏差。

- **情况 A：规范正确，实现有误。** 修复代码，先补充能复现问题的测试，再运行相关回归。不要为了让测试通过而放宽验收标准。
- **情况 B：代码符合现有规范，但规范遗漏了实际需要的行为，或接口无法表达预期结果。** 这不只是实现 bug。先明确预期，追溯到需要修正的需求或设计，转入路径 2 或路径 3，而不是只在代码里打补丁。
- **拿不准是 A 还是 B 时，按 B 处理，停下来问作者。**

**路径 2：执行中需求变了**

先暂停受影响的任务，确认新的目标、范围和验收标准，更新 `proposal.md`；再检查设计与契约是否需要调整、任务是否需要增删或重新拆分、已有代码和测试哪些需要修改。未受影响的成果保留，不必推倒重来。

同步清楚影响后，再依据更新后的规范继续执行。受影响的已完成任务按 4.3 重新打开或新增任务，不能沿用旧的完成状态作为新要求已满足的证据。

**路径 3：需求没变，接口或技术方案需要调整**

从 `design.md` 和相关契约开始修改，涉及关键架构取舍时记录 ADR。随后检查受影响的任务、接口调用方、实现和测试，更新后再继续推进；原有需求仍然成立时，无须重写需求规范。

如果"方案调整"实际上改变了用户可见行为、功能范围或成功标准，就要先回到路径 2 确认需求，不能把需求变化藏在技术修改里。

**路径 4：需求和设计没变，任务粒度或顺序不合理**

直接调整 `tasks.md`：拆分过大的任务、修正依赖、明确各项交付物和验收条件，并同步后续执行安排。已有成果需要对应到调整后的任务中，避免重复实现或遗漏验证。

如果调整任务时发现必须改变模块职责或接口，说明影响已经超出任务层，先回到路径 3 调整设计。

**总结**：从受影响的最上游开始，向下检查；不是每一层都必须修改。只修改受影响的内容，重新验证后再确认完成。

### 4.3 历史维护

- **冲突不要保留**：当前规范失效时，让当前内容反映新的要求和设计，不长期保留相互冲突的有效描述。
- **历史要上库**：规范与代码都纳入版本控制，历史由 Git 保留。
- **决策记录只追加**：ADR 一经确认不再修改。关键决定被替代时，追加新的 ADR，记录取代关系（旧 ADR 的状态改为"已被 NNN 取代"），保留旧决定的理由。
- **任务状态**：
  - 已完成任务一直留在 `tasks.md`，标 `[x]`，不归档。任务超过约 30 项时再考虑归档。
  - 验收标准不变、但支撑它的代码被改动：重新打开，标为 `[~]`，重新通过收尾关卡。
  - 新需求带来新的验收标准：新增任务；旧任务保持 `[x]`，备注"被 Txx 扩展"。
- **记录类文档只追加**：评测报告和实现说明记录的是"当时实际发生了什么"，不修改正文。开头写明所依据的规范版本（commit）；规范变更导致旧结论不再适用时，只在开头追加一行"本报告基于旧规范，最新结果见 xxx"。

### 4.4 版本与提交

- `main` 分支始终保持测试全绿。
- 每个任务开一个分支，例如 `step-02-edit-tool`，在隔离的工作区中进行（superpowers:using-git-worktrees）。
- 提交信息格式：`类型(stepNN): 说明`，类型取 `feat`、`fix`、`test`、`refactor`、`docs`、`eval`。例如 `feat(step02): edit 工具支持唯一匹配校验`。
- 任务合并回 `main` 后打 tag，例如 `step-02`。里程碑额外打版本号：`v0.5`（T5 完成，可写入简历、投寒假实习），`v1.0`（T15 完成）。分支名、提交信息和 tag 中的 `stepNN` 与 `tasks.md` 的任务编号 `TNN` 一一对应。
- 纯措辞修正直接修改，提交类型为 `docs`。
- 评测与版本对应：每份评测报告写明代码 commit 与 tag、模型名称与版本、任务集版本、重复次数。任务集本身也标版本；题目改动后，旧数据不能直接比较，必须用新任务集重跑基线。

### 4.5 规范的反馈回路

同一类问题在对话中被纠正第二次时，AI 应提议把相应的要求补进对应的规范或 `CLAUDE.md`，作者同意后修改。

### 4.6 收尾一致性检查

每个任务收尾时检查：

- `tasks.md` 的状态、完成日期和备注已更新
- `CLAUDE.md` 的规范索引没有过时
- 文档之间的链接没有失效
- 本任务涉及的规范与代码行为一致，没有留下相互冲突的描述

## 附录 B：建议的权限配置（未启用）

以下配置可以把部分规则从"提示词要求"变成"机械强制"，是否启用由作者决定。放在项目的 `.claude/settings.json`：

```json
{
  "permissions": {
    "deny": [
      "Bash(git push:*)",
      "Bash(git merge:*)",
      "Bash(git tag:*)"
    ]
  }
}
```

启用后，AI 无法自行推送、合并或打 tag；需要执行时由作者手动执行，或临时调整配置。
